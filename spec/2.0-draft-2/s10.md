# 10. MCP Binding

## 10.1 Scope

This section maps the Core context operations (5.2) and errors (5.5) onto the Model Context Protocol. It is identified as https://hcp.example/spec/bindings/mcp/2.0 (2.7). It targets MCP version 2026-07-28 and relies on no session state: every request carries its own authorization, as that version of MCP requires.

The MCP Binding carries context operations only. It carries no governance operation (2.6, 6.1.9): grant management, the audit log, export, hard deletion, confirmation, and category changes are reached through the HTTP Binding (9) or the person-facing capabilities required by 18.

The MCP Binding runs over either of MCP's transports:

- **stdio.** Qualifies for the First-Party package only (18). Credentials are obtained from the environment, as MCP specifies for stdio.
- **Streamable HTTP.** Required for the Agent Interop package (18). MCP's authorization, in which the server is an OAuth resource server, is mapped onto the OAuth Interop Profile (13).

## 10.2 Identifying an HCP Server

An HCP Provider exposing the MCP Binding identifies itself in its `server/discover` response, through MCP's `capabilities.extensions` field, under the extension identifier `example.hcp/hcp`. The settings object points to the HCP discovery document and repeats its conformance claims:

    "capabilities": {
      "tools": {},
      "extensions": {
        "example.hcp/hcp": {
          "discovery": "https://provider.example/.well-known/hcp-configuration",
          "conformsTo": [
            "https://hcp.example/spec/core/2.0",
            "https://hcp.example/spec/bindings/mcp/2.0"
          ]
        }
      }
    }

The extension identifier uses the placeholder namespace (2.7) and will change with it. A client determines the HCP protocol version from the discovery document (19). Tool results do not carry it.

This replaces v1's MCP server manifest (v1 Appendix B) and the discovery document's `mcp_manifest_endpoint`, which duplicated what `server/discover` and `tools/list` already provide.

## 10.3 Tools

| Tool | Core operation |
|---------------------------|----------------------|
| `hcp_queryContext` | Query (5.2.1) |
| `hcp_getEntry` | Get entry (5.2.2) |
| `hcp_createEntry` | Create (5.2.3) |
| `hcp_reviseEntry` | Revise (5.2.4) |
| `hcp_withdrawEntry` | Withdraw (5.2.5) |

Requirements for every tool:

- Each tool's `inputSchema` and `outputSchema` reference the Core schemas for its operation (25). A tool MAY expose a subset of the operation's fields (2.5).
- Results are returned in `structuredContent`, conforming to the tool's `outputSchema`. For compatibility, the serialized JSON is also returned in a text content block.
- An HCP Provider MAY limit the tools returned by `tools/list` to those the presented grant permits. MCP allows the list to vary by the authorization on the request.
- A tool call is authorized by the grant presented with it, and the HCP Provider enforces that grant independently of any decision by the MCP host (3.11, invariant 10).

The schemas below are the HCP-specific part of each tool definition.

### 10.3.1 hcp_queryContext

    {
      "name": "hcp_queryContext",
      "description": "Retrieve minimal, relevant entries from the person's HCP instance for a stated purpose.",
      "inputSchema": {
        "type": "object",
        "properties": {
          "query": { "type": "string",
            "description": "Natural language query describing the context or task." },
          "categories": { "type": "array", "items": { "type": "string" },
            "description": "Optional. Categories to search. Omitted means every category the grant can read for the purpose." },
          "purpose": { "type": "string", "format": "uri",
            "description": "Purpose code: one of the purposes the person approved in the grant." },
          "purposeDescription": { "type": "string",
            "description": "Optional. Plain language statement of the task. Logged to audit trail." },
          "maxEntries": { "type": "integer", "default": 5,
            "description": "Maximum entries to return. Default: 5. Maximum: 20." }
        },
        "required": ["query", "purpose"]
      }
    }

The result carries the fields in 5.2.1, including `categoriesSearched`. Each entry is a disclosure (7.4), named by its `ref`; the model receives no stable entry identifier.

### 10.3.3 hcp_createEntry

    {
      "name": "hcp_createEntry",
      "description": "Add a new entry to the person's HCP instance.",
      "inputSchema": {
        "type": "object",
        "properties": {
          "category": { "type": "string", "description": "Category slug." },
          "dimension": { "type": ["string", "null"],
            "description": "Optional. Dimension addressed by this entry, scoped within its category." },
          "content": { "type": "string", "description": "Natural language statement." },
          "declarationType": { "type": "string", "enum": ["person-declared", "model-inferred"] },
          "confidence": { "type": ["string", "null"], "enum": ["high", "medium", "low", null],
            "description": "Required and non-null when declarationType is model-inferred; null or omitted otherwise." },
          "assertedBy": { "type": "string",
            "description": "The Context Asserter. Required when declarationType is model-inferred: identify the model, at a granularity that distinguishes versions." },
          "sourceContext": { "type": "string",
            "description": "Conversation or document ID from which this entry was derived." },
          "relationships": { "type": "array",
            "items": { "type": "object",
              "properties": {
                "type": { "type": "string", "enum": ["derivedFrom", "supersedes", "contradicts", "duplicates"] },
                "target": { "type": "string", "description": "The related entry's ref." } },
              "required": ["type", "target"] },
            "description": "Optional. Relationships this entry has to other entries." }
        },
        "required": ["category", "content", "declarationType", "sourceContext"],
        "allOf": [
          {
            "if": { "properties": { "declarationType": { "const": "model-inferred" } },
                    "required": ["declarationType"] },
            "then": { "required": ["confidence", "assertedBy"],
                      "properties": { "confidence": { "type": "string", "enum": ["high", "medium", "low"] } } },
            "else": { "properties": { "confidence": { "type": "null" } } }
          }
        ]
      }
    }

| Tool field | Core field (5.2.3) |
|-----------------|---------------------------------------------|
| `category` | `classification.category` |
| `dimension` | `classification.dimension` |
| `content` | `content.value`, with `content.profile` set to the General Context Profile (11) |
| `declarationType` | `assertion.declarationType` |
| `confidence` | `assertion.confidence` |
| `assertedBy` | `record.provenance.assertedBy.id` |
| `sourceContext` | `record.provenance.source` |
| `relationships` | `relationships` (4.2.3) |

This tool creates General Context entries only: `content` carries a natural language statement, and the tool provides no means of supplying evidence, so entries it creates carry none. Its `declarationType` enum omits `issuer-attested` as a subset of the Core operation (2.5). That a Context Client cannot attest on an issuer's behalf is a Core rule (3.7), not a consequence of this tool's shape. Entries carrying a credential, and other `issuer-attested` entries, are created through the HTTP Binding (9.4.3).

A write that violates the `confidence` rule in 5.2.3 is rejected with invalid request (10.4).

## 10.4 Errors

MCP distinguishes protocol errors from tool execution errors. The MCP Binding uses them as follows:

- A request that MCP itself cannot accept --- an unknown tool, or a request that fails MCP's own `tools/call` schema --- is a protocol error, returned as a JSON-RPC error.
- Every Core error (5.5), including invalid request, is returned as a tool execution error, except as the two items on HTTP below state: a result with `isError: true` whose `structuredContent` carries the error's code (5.5) as `type` and a human-readable `detail`, with the same text in a text content block. Each tool's `outputSchema` admits this error object as an alternative to the operation's result.
- Over Streamable HTTP, a request with missing, invalid, or expired authorization is rejected at the HTTP layer with status 401, as MCP's authorization requires. This is how the binding reports unauthenticated.
- Over Streamable HTTP, a not authorized denial that follows from the request alone --- a category, action, or purpose the grant does not cover --- is rejected at the HTTP layer with status 403 and a `WWW-Authenticate` challenge with error `insufficient_scope`, as MCP's authorization recommends. The challenge's `scope` names the scopes the request needs. A challenge cannot name a purpose, so where the denial is for purpose alone, its `error_description` names the purpose code the request used. The MCP host, which holds the grant (10.5), can then ask the Authorizing Principal for a new or wider grant (6.1.6), requesting the purpose with authorization details (13.3).
- A not authorized denial that depends on what is stored --- an entry outside the grant, or one that does not exist --- is returned as a tool execution error carrying `scope-denied`. It never produces a challenge, because a challenge would show that the entry exists (5.2.2).

A tool execution error carrying a Core error:

    {
      "isError": true,
      "structuredContent": { "type": "scope-denied", "detail": "Entry not available under this grant." },
      "content": [ { "type": "text", "text": "scope-denied: Entry not available under this grant." } ]
    }

A not authorized result MUST NOT disclose whether a requested entry exists (5.2.2).

Over stdio there is no HTTP layer, and every not authorized denial is a tool execution error.

The split follows who can act on the denial. A 403 reaches the host, which holds the grant and can ask the person for more; a tool execution error reaches the model, which can only work within what it has.

## 10.5 Who Holds the Grant

A grant authorizes an HCP Client (6.1.8). Under the MCP Binding:

- The grant is held by the component that presents credentials: the MCP host or its HCP integration. It is never held by the model (3.11, invariants 6 and 9).
- The access token MUST NOT enter the model's context, and MUST NOT be returned as tool content (3.11, invariant 14).
- A host's permission to call a tool does not substitute for the grant, and a grant does not oblige a host to call a tool (3.11, invariant 10).
- A local stdio bridge to a remote HCP Provider is an HCP Client in its own right. It holds the token, calls the provider over the HTTP Binding, has its own Client Operator (3.2.8), and is bound by every rule for HCP Clients, including onward disclosure (3.12).
