# Part III --- Profiles

A profile adds stricter rules to Core for a domain, a security posture, an evidence type, or a deployment pattern (2.2). Each profile in this Part has its own conformance identifier (2.7), and an implementation conforms to a profile only by listing that identifier in `conformsTo` (19). Claiming a profile requires conforming to Core. Which profiles each package requires is set out in 18.

| Profile | Required by |
|-------------------------------------|----------------------------------------------------------|
| General Context (11) | Every package |
| First-Party Authorization (12) | The First-Party package |
| OAuth Interop (13) | The Provider Interop and Agent Interop packages |
| VC Evidence (14) | No package; adds to any package |
| Memory Manager (15) | Any HCP Provider that accepts `model-inferred` entries (4.7) |
| Health Context (16.2) | Any HCP Provider that accepts `issuer-attested` entries in `health_context` (16.1) |
| Education Context (16.4) | Any HCP Provider that accepts `issuer-attested` entries in `education_learner_profile` (16.1) |
| Delegated Authorization (17) | Any implementation that issues a grant authorized by a party other than the Context Subject (17.1) |

# 11. General Context Profile

## 11.1 Scope

This profile defines the content profile for statements: structured natural language, or a structured object, in the entry defined in 4.2. It is identified as https://hcp.example/spec/profiles/general-context/2.0 (2.7), and it is required in every package (18). The same identifier is the value of `content.profile` for an entry whose content has the shape defined here.

An implementation conforming to this profile MUST accept and emit entries whose `content` has the shape defined in this section. Validation is JSON Schema validation against the published schema (4.1.1, 25).

## 11.2 Content

    "content": {
      "profile": "https://hcp.example/spec/profiles/general-context/2.0",
      "value": "{natural language statement or structured object}",
      "language": "{BCP 47 language tag | null}"
    }

| Field | Required | Set by | Description |
|------------------------------|-------------|--------------------------|----------------------------------------------------|
| `content.profile` | Yes | HCP Client | This profile's identifier |
| `content.value` | Yes | HCP Client | String or Object. The statement. |
| `content.language` | No | HCP Client | The language of a string `value` |

Requirements:

- An entry whose `assertion.validUntil` has passed is `expired` (4.2.4). It is not disclosed to a Context Client, and it remains visible to the Context Subject.
- An entry with this content profile MAY carry evidence items whose `role` is `supports` (4.2.2). It carries none whose `role` is `content`.

## 11.3 Relationship

`subject.relationship` is reserved. It describes the relationship between the Context Subject identified in `subject.id` and the party who declared or administers the entry, where these differ. This specification assigns no behavior to this field.

The field is reserved for forward compatibility. Implementations MUST NOT interpret its presence, absence, or value as conferring, extending, or limiting authorization. Delegated authority is recorded on a delegation under the Delegated Authorization Profile (17.2), not in this field. The field exists so that deployments that record who declared or administers an entry do so in one shape rather than inventing one per deployment. No vocabulary is registered for it.

## 11.4 Example

An entry with this content profile as the Context Subject sees it, through export or a Management Client. A Context Client receives the same entry with the fields in 7.4 omitted; 9.4.2 shows that form.

    {
      "@context": ["https://hcp.example/contexts/v2"],
      "schema": "https://hcp.example/spec/entry/2.0",
      "id": "urn:uuid:7f3a1b2c-4d5e-6f7a-8b9c-0d1e2f3a4b5c",
      "type": ["ContextEntry"],
      "subject": { "id": "did:example:subject-a3f9", "relationship": null },
      "content": {
        "profile": "https://hcp.example/spec/profiles/general-context/2.0",
        "value": "I require high arch support in footwear due to a diagnosed condition.",
        "language": "en"
      },
      "assertion": {
        "declarationType": "person-declared",
        "confidence": null,
        "validUntil": null
      },
      "classification": {
        "category": "health_context",
        "dimension": "footwear_support"
      },
      "evidence": [],
      "record": {
        "status": "active",
        "version": 1,
        "provenance": {
          "assertedBy": { "id": "did:example:subject-a3f9", "assurance": "unverified" },
          "assertedAt": "2026-06-15T10:30:00Z",
          "source": "conversation-id:abc123",
          "submittedByClient": {
            "id": "https://assistant.example/clients/hcp",
            "name": "Example Assistant",
            "operator": { "id": "https://assistant.example", "name": "Example Assistant Co." }
          },
          "authorizedUnder": "urn:uuid:5b1d9e3a-2c47-4f80-9a61-0e8c7d2b4f13",
          "recordedByProvider": "https://provider.example",
          "recordedAt": "2026-06-15T10:30:02Z",
          "confirmations": [
            {
              "disposition": "confirmed",
              "confirmedBy": { "id": "did:example:subject-a3f9" },
              "confirmedAt": "2026-06-16T08:12:40Z"
            }
          ]
        },
        "relationships": []
      }
    }

The assistant submitted the statement as `person-declared`, so the provider recorded assurance `unverified` (3.7). The Context Subject later confirmed it through a Management Client, which gives the entry standing in a conflict (3.8). In v1 this entry carried `userVerified: true`; that field is removed (3.5), and a v1 entry carrying it is converted as 4.3 sets out.
