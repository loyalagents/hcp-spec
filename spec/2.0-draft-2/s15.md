# 15. Memory Manager Profile

## 15.1 Scope

Core defines what happens when two entries conflict, and that they conflict when a `contradicts` relationship links them (4.2.3, 4.7). This profile defines how an HCP Provider finds conflicts itself. It is identified as https://hcp.example/spec/profiles/memory-manager/2.0 (2.7). An HCP Provider that accepts `model-inferred` entries MUST conform to it (4.7); an HCP Provider that accepts none need not.

v1's matching rule --- two entries with the same category and the same normalized dimension conflict --- is removed. Two entries can address the same dimension without contradicting each other, and genuinely contradictory entries can carry different dimensions. Automated reconciliation is planned for Draft 3 (26).

## 15.2 Candidates

A candidate conflict is between an entry with `assertion.declarationType` `model-inferred` and an active entry with `assertion.declarationType` `person-declared`. Detection is symmetric and MUST be evaluated on every write, whichever of the two is written second.

- The HCP Provider MUST apply a detection method --- structural comparison, term overlap, semantic judgment, or any other --- and MUST declare it in its discovery document as `conflict_detection` (19). The set of values is open.
- Where the method finds that the two entries cannot both be true, the HCP Provider MUST record a `contradicts` relationship between them (4.2.3), with `assertedBy` naming the provider in the role `hcp-provider` (3.9).
- `classification.dimension` is a hint. A method MAY use it, but two entries MUST NOT be found to conflict on the basis of sharing a dimension alone. Before comparing two dimensions, a provider SHOULD normalize each: trim surrounding whitespace, lowercase, and collapse internal whitespace to a single underscore. No dimension vocabulary is registered (4.2, 26).
- Conflicts involving an `issuer-attested` entry, conflicts between two `person-declared` entries, and conflicts between two `model-inferred` entries are outside the scope of this profile (4.4, 4.7).

Which entry is set to `conflicted` once a conflict is asserted depends on standing, and is defined in Core (4.7.1, 4.7.2). Under v1 the `user-declared` entry always prevailed; under v2 an `unverified` `person-declared` entry does not, and both entries are quarantined until the Context Subject resolves the conflict (3.7).

## 15.3 Re-evaluation

Detection runs on every write, including a revision. Where a revision of an entry in a conflict means the method no longer finds the conflict, the HCP Provider removes the `contradicts` relationship it asserted, and the resolution rule in 4.7.3 applies: any entry quarantined by the conflict returns to `active`, and a `conflict.resolved` event is appended.
