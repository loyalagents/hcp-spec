# Part IV --- Conformance

This Part states how an implementation claims conformance (18), how it describes itself (19), and how its claims are tested (20). Its requirements apply to every implementation that makes a claim. The Part has no conformance identifier of its own and is not itself claimed (2.1).

# 18. Conformance Claims and Packages

## 18.1 Claims

An implementation states what it conforms to as a `conformsTo` list of conformance identifiers (2.7) in its discovery document (19).

- An implementation claiming any HCP conformance MUST list Core, and MUST list every binding and every profile it claims.
- An implementation MUST NOT list an identifier unless it satisfies every requirement of that Part. A binding or profile is claimed whole.
- An implementation that accepts `model-inferred` entries MUST list the Memory Manager Profile (4.7).
- An implementation that accepts `issuer-attested` entries in `health_context` MUST list the Health Context Profile, and one that accepts them in `education_learner_profile` MUST list the Education Context Profile. Either requires listing the VC Evidence Profile (16.1).
- An implementation that issues a grant whose Authorizing Principal is not the Context Subject MUST list the Delegated Authorization Profile (17.1).

The `conformsTo` list is authoritative. A client determines what an implementation supports from that list, whatever is claimed for the implementation elsewhere (12.2).

In this draft a claim is made for an HCP Provider, together with the Authorization Service where the two are deployed together (3.2.5). Requirements this specification places on HCP Clients, such as the actor invariants (3.11) and onward disclosure (3.12), apply to every client wherever they are stated, but a client has no conformance claim of its own. Client conformance claims are noted for a later draft (26).

## 18.2 Packages

A package names a combination of Parts that implementations commonly claim. A package has no identifier of its own: an implementation claims a package by listing every identifier the package comprises.

| Package | Lists in `conformsTo` | Bindings | v1 equivalent |
|-----------------|------------------------------------------------------|------------------------------------------|----------------|
| First-Party | Core, General Context, First-Party Authorization, and each binding exposed | Either or both; MCP over either transport | Core |
| Provider Interop | Core, General Context, HTTP Binding, OAuth Interop | HTTP required; MCP permitted | Interop |
| Agent Interop | Everything Provider Interop lists, and the MCP Binding | HTTP, and MCP over Streamable HTTP | None |
| VC Evidence | The VC Evidence Profile, added to any package above | As for that package | VC-Extended |

- **First-Party.** For an implementation whose HCP Clients are all operated by its own Provider Operator (12.1). Grants are obtained under the First-Party Authorization Profile (12), and the implementation may expose any one binding or both.
- **Provider Interop.** The common provider baseline. The HTTP Binding carries both the context and the governance planes (2.6), and grants are obtained under the OAuth Interop Profile (13).
- **Agent Interop.** Provider Interop with agent-native access added. The MCP Binding runs over Streamable HTTP, with MCP's authorization mapped onto the OAuth Interop Profile (10.1, 13.5). MCP over stdio does not qualify (10.1).
- **VC Evidence.** Adds entries whose content is a credential to any package (14).

The Memory Manager Profile (15), the Health and Education Context Profiles (16), and the Delegated Authorization Profile (17) are added to any package where they apply (18.1). Each of the Health and Education Context Profiles brings the VC Evidence Profile with it.

## 18.3 When Provider Interop Is Required

An implementation that accepts, or holds itself out as accepting, authorization requests from any HCP Client whose Client Operator is not its own Provider Operator MUST claim the Provider Interop package.

It follows that:

- The HTTP Binding is required of every implementation that accepts HCP Clients operated by others. An implementation whose only binding is MCP accepts first-party clients only.
- An implementation claiming the First-Party Authorization Profile cannot claim Provider Interop or Agent Interop (12.2).

Under v1, an implementation accepting outside clients over MCP alone could claim Interop. Under this draft it cannot.

## 18.4 Person-Facing Capabilities

Each capability below MUST be available through at least one modality the implementation supports. These are capabilities, not interface requirements; natural language is a conformant modality (18.5).

- The Context Subject can enumerate all stored entries, including those whose `record.status` is `conflicted`.
- The Context Subject can correct or delete any entry, and can request hard deletion (5.4.2).
- The Context Subject can resolve a conflict by rejecting, accepting, or superseding an entry (4.7.3).
- The Authorizing Principal can enumerate and revoke all active grants, represented per 6.1.5, with the approved purposes shown (6.1.5.2) and any narrowing reflected per 6.1.5.1.
- The Authorizing Principal can view the audit log (8.3), and the disclosure summary (8.6).
- The Authorizing Principal is told when a revocation notification could not be delivered, and when the client's copies stop being usable (6.2.4).
- The Authorizing Principal is told, before approving and at revocation, which client keeps copies under a declared legal obligation (6.1.6, 6.2.5).
- The Context Subject can set and remove standing rules, and is told when one excludes a requested category (6.3).
- Authorization interactions make temporary access the default outcome, and electing persistence requires a separate affirmative act (6.1.4).
- Where a bounded audit durability window is declared, it is disclosed wherever the audit log is presented (8.4).
- Under the Delegated Authorization Profile: the Context Subject and each delegate can read the delegations that name them (17.2); the Context Subject can revoke any grant made for them (17.5); the person is shown the summary of a delegated period at the age of majority (17.6), and is told wherever their audit log is presented that a former delegate can read part of it (17.7).

An implementation exposing the HTTP Binding MAY provide these capabilities through a Management Client over that binding. An implementation whose only binding is MCP, permitted under the First-Party package, provides them through its own person-facing interface (2.6).

## 18.5 Natural Language Access in LLM-Mediated Contexts

In contexts where an LLM is the primary interface --- for example, an AI assistant through which a person manages their HCP instance --- implementations MAY provide the person-facing capabilities (18.4) through natural language interaction rather than a graphical interface.

This includes operations such as:

- Viewing stored entries (e.g., "show me what you know about my learning preferences")
- Correcting an entry (e.g., "that's wrong; I prefer worked examples, not videos")
- Deleting an entry (e.g., "forget what I said about my schedule constraints")
- Reviewing active grants (e.g., "which apps have access to my health context?")
- Revoking a grant (e.g., "remove access for the recipe app")

Requirements for natural language access:

- The underlying operations MUST map to the Core operations defined in 5 and the grant operations defined in 6.
- The audit log MUST capture these operations identically to their equivalents in a binding; the interface modality does not change the audit requirement.
- The implementation MUST confirm the action to the person in natural language before executing writes, updates, or deletions.
- The implementation MUST NOT execute irreversible operations (hard deletion, grant revocation) without explicit confirmation by the person in the same interaction.

Where the LLM-mediated interface is an HCP Client, it reaches governance operations as a Management Client over the HTTP Binding (2.6). The Management Client's credentials are held by the client, never by the model (10.5), and a confirmation is the person's own act: a model's judgment that the person would agree does not satisfy it (3.11, invariant 6).

HCP is a protocol, not a user experience pattern, and implementations are free to design elicitation and interaction flows appropriate to their context (Part V). This section establishes only that natural language is a conformant modality for the operations listed above, subject to the requirements stated here.
