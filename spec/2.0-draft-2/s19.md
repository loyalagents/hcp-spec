# 19. Discovery Document

## 19.1 Publication

Every implementation claiming HCP conformance MUST publish a discovery document, as JSON.

- An implementation exposing the HTTP Binding publishes it at `/.well-known/hcp-configuration` relative to its base URL (9.1).
- An implementation whose only binding is MCP publishes it at an HTTPS URL, and names that URL in the `discovery` setting of its MCP extension (10.2).

Where the `conformsTo` list in an MCP server's extension settings (10.2) differs from the discovery document's, the discovery document governs.

Conformance identifiers in the document are compared as exact strings and need not resolve (2.7).

## 19.2 Example

    {
      "hcp_version": "2.0",
      "provider": "{base-url}",
      "provider_operator": { "id": "{operator-identifier}", "name": "{organization name}" },
      "conformsTo": [
        "https://hcp.example/spec/core/2.0",
        "https://hcp.example/spec/bindings/http/2.0",
        "https://hcp.example/spec/bindings/mcp/2.0",
        "https://hcp.example/spec/profiles/general-context/2.0",
        "https://hcp.example/spec/profiles/oauth-interop/2.0",
        "https://hcp.example/spec/profiles/memory-manager/2.0",
        "https://hcp.example/spec/profiles/vc-evidence/2.0",
        "https://hcp.example/spec/profiles/delegated-authorization/2.0"
      ],
      "bindings": ["http", "mcp"],
      "protected_resource_metadata": "{base-url}/.well-known/oauth-protected-resource",
      "jwks_uri": "{base-url}/.well-known/jwks.json",
      "entries_endpoint": "{base-url}/v2/entries",
      "grants_endpoint": "{base-url}/v2/grants",
      "audit_endpoint": "{base-url}/v2/audit",
      "export_endpoint": "{base-url}/v2/export",
      "delegations_endpoint": "{base-url}/v2/delegations",
      "rules_endpoint": "{base-url}/v2/rules",
      "mcp_endpoint": "{base-url}/mcp",
      "supported_categories": [
        "general_preferences", "goals_and_constraints", "health_context",
        "education_learner_profile", "work_context", "purchase_history_preferences",
        "values_and_ethics", "location_context", "coordination_context"
      ],
      "category_registry": "1",
      "accepts_entry_schemas": ["https://hcp.example/spec/entry/2.0"],
      "minimization_method": "semantic",
      "conflict_detection": "semantic",
      "audit_durability": {
        "default": "synchronous",
        "bounded": { "context.read": 5000 }
      },
      "audit_integrity": "hash-chained",
      "pagination": { "audit": "cursor" },
      "problem_type_base": "https://hcp.example/problems/",
      "rate_limits": { "documentation_url": "{url}" },
      "vc_securing": {
        "issues": ["eddsa-rdfc-2022"],
        "verifies": ["eddsa-rdfc-2022", "ecdsa-sd-2023", "vc-jose-cose"]
      },
      "credential_status_interval": 3600
    }

The example is an Agent Interop implementation that also claims VC Evidence and the Delegated Authorization Profile, and that accepts `model-inferred` entries and so claims the Memory Manager Profile (18.1, 18.2).

## 19.3 Members

| Member | Presence | Meaning |
|--------------------------|----------------------------------------|----------------------------------------------------------|
| `hcp_version` | Required | The protocol version. Every HTTP response carries it in the `HCP-Version` header (9.3). |
| `provider` | Required | The HCP Provider's base URL. Named so that "issuer" refers only to a credential issuer (3.2.6). |
| `provider_operator` | Required | The Provider Operator: an identifier and a name the person can recognize (3.2.8). |
| `conformsTo` | Required | The conformance claims (18.1) |
| `bindings` | Required | The bindings exposed: `http`, `mcp`, or both (2.5). Each binding listed here has its identifier in `conformsTo`, and each binding claimed there is listed here. |
| `protected_resource_metadata` | Required under the OAuth Interop Profile (13) | The URL of the provider's OAuth 2.0 Protected Resource Metadata (RFC 9728), which names its Authorization Service (13.5) |
| `entries_endpoint`, `grants_endpoint`, `audit_endpoint`, `export_endpoint` | Required where the HTTP Binding is exposed | The HTTP Binding's endpoints (9.2) |
| `mcp_endpoint` | Required where the MCP Binding runs over Streamable HTTP | The MCP endpoint (10.1) |
| `delegations_endpoint` | Required under the Delegated Authorization Profile where the HTTP Binding is exposed | The delegations endpoint (9.4.13) |
| `rules_endpoint` | Required where the HTTP Binding is exposed | The standing rules endpoint (9.4.14) |
| `jwks_uri` | Required | The JSON Web Key Set holding the keys that sign revocation notifications (9.9) |
| `supported_categories` | Required | The categories the implementation holds, registered and custom (4.5) |
| `category_registry` | Required | The version of the category registry used (4.5, 25.1) |
| `accepts_entry_schemas` | Required | The entry schemas accepted: this draft's, and any v1 forms accepted on import (4.3). Entries are always emitted in the form of 4.2. |
| `minimization_method` | Required | The relevance method determining the final ordering of query results (7.3). The set of values is open. `none` is not a valid declaration, because a query always applies an ordering. |
| `conflict_detection` | Required under the Memory Manager Profile; omitted otherwise | The method by which the provider finds conflicts (15.2). The set of values is open. |
| `audit_durability` | Required | `default` is `synchronous`. `bounded` declares a durability window in milliseconds; it MAY be declared only for `context.read`, within the limit in 8.4. An implementation with no window omits `bounded`. |
| `audit_integrity` | Required | The integrity level of the Context Subject's audit log: `append-only`, `hash-chained`, `signed-checkpoints`, or `anchored` (8.7) |
| `pagination` | Required where the HTTP Binding is exposed | Pagination of the audit log (9.5) |
| `problem_type_base` | Required where the HTTP Binding is exposed | The base of the problem types (9.7) |
| `rate_limits` | Recommended | The rate limit policy (9.8) |
| `vc_securing` | Required under the VC Evidence Profile; omitted otherwise | The securing mechanisms issued and verified (14.5): `eddsa-rdfc-2022`, `ecdsa-sd-2023`, `vc-jose-cose`. `verifies` always includes `eddsa-rdfc-2022`. |
| `credential_status_interval` | Required under the VC Evidence Profile; omitted otherwise | The greatest age, in seconds, of the status list copy from which credential status is established: at most 86400, or 3600 under the Health Context Profile (14.7, 16.2) |

## 19.4 Changes from v1

| v1 member | v2 |
|--------------------------|------------------------------------------------------------------|
| `conformance_level` | Replaced by `conformsTo` (18.1) |
| `supported_transports` | Replaced by `bindings` (2.5) |
| `authorization_profile` | Removed. `conformsTo` names the authorization profile (12.2, 13.1) |
| `mcp_manifest_endpoint` | Removed. An MCP server identifies itself through `server/discover` (10.2) |
| --- | `provider_operator` added (3.2.8) |
| --- | `mcp_endpoint` added |
| `issuer` | Renamed `provider` (3.2.6) |
| `preferences_endpoint` | Renamed `entries_endpoint` |
| `envelope_form` | Replaced by `accepts_entry_schemas` (4.3) |
| `tier2_securing` | Renamed `vc_securing` (14.5). `data-integrity` becomes `eddsa-rdfc-2022`; `ecdsa-sd-2023` is added |
| --- | `category_registry` and `conflict_detection` added |
| `authorization_endpoint`, `token_endpoint`, `revocation_endpoint` | Replaced by `protected_resource_metadata` (13.5) |
| --- | `jwks_uri` and `audit_integrity` added |
| --- | `credential_status_interval` added (14.7) |
| --- | `delegations_endpoint` added (9.4.13) |
| --- | `rules_endpoint` added (9.4.14) |

The member name `storage_encryption` is reserved for the declaration of end-to-end encrypted storage that v1 placed on record (26).
