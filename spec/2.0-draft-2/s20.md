# 20. Conformance Testing

This section describes the HCP Conformance Test Suite. It places no requirement on implementations beyond those in the sections it cites.

## 20.1 Scope of the Suite

The suite, to be published alongside this specification, will provide:

- Automated schema validation of entries against the published JSON Schema (4.1.1, 25), and of credentials under the VC Evidence Profile (14).
- Grant semantics tests --- category scoping, temporary-by-default, expiry bounds, revocation propagation, and the prohibition on silent scope expansion --- applicable to all implementations, verified against the grant representation in 6.1.5.
- An OAuth 2.0 grant flow test harness, applicable to implementations claiming the OAuth Interop Profile (13).
- Minimization tests: out-of-scope entries are not returned (7.1); the quantity bound holds and results are not padded, verified against seeded fixtures in which the number of matching entries is known (7.2); the declared relevance method matches the discovery document (7.3); redacted fields are absent from responses to a Context Client and reported in `redactedFields` (7.4, 7.5).
- Audit log completeness tests (8.1), including the participants each event names (3.9).
- Revocation propagation tests (6.2).
- Provenance tests: fields the HCP Provider sets are not taken from a request, and assurance is never recorded higher than was established (3.5--3.7).
- Governance plane tests: every governance operation fails with not authorized for a Context Client, and the MCP Binding carries none (6.1.9, 10.1).
- Binding tests: each claimed binding maps the Core operations and errors as specified (9, 10).

The suite exercises a materially larger surface than the June 2026 draft of v1 implied: v1 entries converted on import (4.3); grant semantics verified against a grant representation that includes narrowed grants (6.1.5, 6.1.5.1); a four-part minimization contract requiring seeded fixtures (7); conflict outcomes in Core (4.7) and conflict detection, including dimension normalization, under the Memory Manager Profile (15); three declaration types and three assurance values (4.4, 3.6); one mandatory securing mechanism among three, and credential status against seeded status lists (14.5, 14.7); and two bindings (9, 10).

Schema validation is the suite's first function, so the suite depends on the entry JSON Schema being published (25).

## 20.2 Test Hook for First-Party Implementations

An implementation claiming the First-Party Authorization Profile still requires a means for the suite to obtain a credential and trigger grant creation (12.2). The suite specification defines a test hook for this purpose.

A grant created through the hook is not created by an act of the Authorizing Principal. A deployment holding any real person's context therefore cannot offer the hook without failing 6.1.6.

## 20.3 Pilots

Pilot implementations are expected to run the test suite before integration with field pilots (21).
