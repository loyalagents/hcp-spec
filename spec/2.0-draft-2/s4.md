# 4. Data Model

## 4.1 Overview

An HCP entry describes the Context Subject through independent properties:

| Property | What it holds | Set by | Defined in |
|-----------------------|------------------------------------------------|------------------------------------------------------------|----------------------|
| `subject` | Who the entry is about | HCP Client; MUST identify the Context Subject | 4.2 |
| `content` | What is said, in the shape a content profile defines | HCP Client | 4.2; General Context Profile (11) |
| `assertion` | What kind of party said it, how confident it is, and until when it holds | HCP Client | 4.2, 4.4 |
| `classification` | Which category it belongs to, and the dimension it addresses | HCP Client on create; afterwards only by governance (4.2.1) | 4.2, 4.5 |
| `evidence` | Credentials that are the content, or that support it | HCP Client | 4.2.2; VC Evidence Profile (14) |
| `record` | Lifecycle, version, provenance, and relationships | HCP Provider | 4.2, 3.5, 4.2.3 |

The properties vary independently. A statement the Context Subject made about a health condition is high-sensitivity without carrying any credential; an Open Badges credential carries a proof without being sensitive; and either may be inferred, declared, or attested. This section defines the entry, declaration types, the category vocabulary, and what Core requires when entries conflict.

## 4.1.1 Processing Requirements

Conformance requires no JSON-LD processing.

- The `@context` array is a fixed constant. Implementations MUST emit it exactly as specified in 4.2 and MAY compare it literally on ingest.
- Implementations are not required to perform JSON-LD expansion, compaction, flattening, framing, or RDF canonicalization, and are not required to embed a JSON-LD processor.
- Validation of an entry is JSON Schema validation against the schema published alongside this specification (25).
- An implementation that treats entries as plain JSON documents carrying a constant `@context` is fully conformant to Core.

A credential in `evidence` may be secured with a mechanism that requires canonicalization (14). That requirement is confined to the credential.

## 4.2 Entry

Every HCP entry is a JSON document conforming to the following structure. It has one form (4.3).

    {
      "@context": ["https://hcp.example/contexts/v2"],
      "schema": "https://hcp.example/spec/entry/2.0",
      "id": "urn:uuid:{entry-uuid}",
      "type": ["ContextEntry"],
      "subject": { "id": "{subject-identifier}", "relationship": null },
      "content": { },
      "assertion": {
        "declarationType": "person-declared | model-inferred | issuer-attested",
        "confidence": "{high | medium | low | null}",
        "validUntil": "{ISO-8601 | null}"
      },
      "classification": {
        "category": "{category-slug}",
        "dimension": "{dimension-string | null}"
      },
      "evidence": [ ],
      "record": { }
    }

`subject.id` MUST identify the Context Subject of the HCP instance that holds the entry (3.11, invariant 2). The subject identifier MAY be any URI, including a pseudonym the HCP Provider issues. HCP defines no DID method. `subject.relationship` is reserved (11.3).

`content` is what is said about the Context Subject. Its shape is named by `content.profile`, a URI. This specification defines two content profiles: the General Context Profile, for statements in natural language or as structured objects (11), and the VC Evidence Profile, for an entry whose content is a credential (14). Where the content is a credential, `content` names the evidence item that holds it instead of restating it (4.2.2).

`assertion` is what the submitting HCP Client states about the assertion: what kind of party made it (4.4), how confident an inferring model is (4.4), and `validUntil`, the time after which the content no longer holds. `validUntil` describes the content. It is not the time after which a client may no longer use a disclosed copy (7).

`classification` is HCP's classification of the entry. It sits apart from `content` and `evidence` because HCP determines it: an issuer of a Verifiable Credential has no reason to know HCP's category vocabulary, and category governs authorization scope, which is not an issuer's decision to make.

`schema` identifies the version of this entry structure. It is required on every entry, including entries in an export, and its value in this draft is `https://hcp.example/spec/entry/2.0`, compared as an exact string (2.7). An HCP Provider MUST reject with invalid request (5.5) a write naming a schema it does not accept (4.3).

### record

    "record": {
      "status": "active | deprecated | conflicted | expired | revoked | suspended | deleted",
      "version": 1,
      "provenance": {
        "assertedBy": {
          "id": "{identifier}",
          "assurance": "unverified | authenticated | cryptographically-verified"
        },
        "assertedAt": "{ISO-8601}",
        "source": "{conversation-id | document-id | person-input | integration}",
        "submittedByClient": {
          "id": "{client-identifier}",
          "name": "{client name}",
          "operator": { "id": "{operator-identifier}", "name": "{organization name}" }
        },
        "authorizedUnder": "{grant-id}",
        "recordedByProvider": "{provider-identifier}",
        "recordedAt": "{ISO-8601}",
        "confirmations": [
          {
            "disposition": "confirmed | rejected",
            "confirmedBy": { "id": "{identifier}" },
            "confirmedAt": "{ISO-8601}"
          }
        ]
      },
      "relationships": [
        {
          "type": "derivedFrom | supersedes | contradicts | duplicates",
          "target": "{entry-id}",
          "assertedBy": { "role": "{role}", "id": "{identifier}" },
          "recordedAt": "{ISO-8601}"
        }
      ]
    }

`record.provenance` records who asserted, submitted, authorized, recorded, and confirmed each version of the entry. Its rules are in 3.5–3.8. `record.relationships` is defined in 4.2.3, and `record.conversion`, present only on an entry converted from v1, in 4.3.

### Required Fields

| Field | Type | Description |
|-------------------------------------------|------------|------------------------------------------------------------------|
| `schema` | URI | The entry structure version |
| `id` | URN (UUID) | Globally unique entry identifier. Stable across all versions of the entry; never reassigned on revision. |
| `type` | Array | Must include "ContextEntry" |
| `subject.id` | URI | The Context Subject |
| `content.profile` | URI | The content profile defining the shape of `content` |
| `assertion.declarationType` | Enum | `person-declared`, `model-inferred`, or `issuer-attested`; never omitted. See 4.4. |
| `classification.category` | String | Category slug from the registered category vocabulary, or a custom category URI (4.5) |
| `record.provenance.assertedBy.id` | String | The Context Asserter (3.5) |
| `record.provenance.assertedBy.assurance` | Enum | How the asserter's identity was established (3.6) |
| `record.provenance.assertedAt` | ISO-8601 | When the assertion was made, as the submitting client states it |
| `record.provenance.source` | String | Origin of the entry, as the submitting client states it |
| `record.provenance.submittedByClient` | Object | The HCP Client that submitted this version, and its operator (3.5) |
| `record.provenance.authorizedUnder` | String | The grant under which this version was written |
| `record.provenance.recordedByProvider` | String | The HCP Provider that recorded this version |
| `record.provenance.recordedAt` | ISO-8601 | When the provider recorded this version |
| `record.version` | Integer | Monotonically increasing revision number, starting at 1 |
| `record.status` | Enum | Lifecycle state of the entry |

The `record.version` field is a positive integer beginning at 1. Each successful revision MUST increment `record.version` by exactly 1. Implementations MUST NOT skip or reuse version numbers within an entry's revision history. Revision history is linear: the version preceding version *n* is *n* − 1, and a revision names the version it revises (5.2.4). `record.provenance.recordedAt` of the current version is the time the entry was last revised.

No UUID version is mandated for `id`: any RFC 4122 version MAY be used, and implementations MUST NOT assume or require a particular one.

The fields required in `content` are defined by its content profile (11, 14).

### Optional Fields

| Field | Notes |
|--------------------------------------|------------------------------------------------------------------|
| `assertion.confidence` | MUST be present and non-null when `assertion.declarationType` is `model-inferred`. MUST be null or omitted for any other declaration type. |
| `assertion.validUntil` | If absent or null, the content does not expire. |
| `classification.dimension` | Free-form identifier for the dimension addressed by the entry, scoped within its category. A hint for conflict detection (15). No vocabulary is registered. |
| `evidence` | Evidence items (4.2.2). Absent or empty when the entry carries none. |
| `record.provenance.confirmations` | Confirmation records for this version (3.8). Absent or empty when the version has none. |
| `record.relationships` | Relationships to other entries (4.2.3). Absent or empty when there are none. |
| `record.conversion` | Present only on an entry converted from v1 (4.3). |
| `record.metadata` | Optional. Object. Free-form key-value data an implementation attaches to the entry for its own purposes --- internal identifiers, application tags, integration bookkeeping. Not part of the assertion and not interpreted by HCP. |

`classification.dimension` is scoped within `classification.category`: the same string under two different categories denotes two different dimensions and MUST NOT be treated as a match.

`record.metadata` carries no HCP-defined meaning and MUST NOT be used to store data that affects category, scope, or authorization. Conflict handling (4.7), minimization (7), and grant restrictions (6.1.5.1) operate over the fields those sections name, not over `metadata`. No vocabulary is registered, and `metadata` contents are not guaranteed portable across implementations.

An HCP Provider MUST preserve members of an entry that this specification does not define and MUST NOT interpret them (25.3).

## 4.2.1 Mutability

These rules are stated as behavior observable across a binding or in an export (2.4).

- Once a version of an entry has been exposed, its `content`, `assertion`, and `evidence` MUST NOT change. A change to any member of them produces a new version, and `record.version` increments. The one exception is `verification` on an evidence item, which the HCP Provider updates when a credential's status changes (4.2.2, 14.7).
- A change to a credential in `evidence` requires a new credential from its issuer. The HCP Provider MUST NOT alter a credential.
- `subject` MUST NOT change.
- The fields in `classification` and `record` MAY change without a new version, with one exception: `record.provenance` belongs to a version and is fixed when that version is recorded, apart from confirmation records appended to it (3.8). No credential's proof covers `classification` or `record`.
- `classification.category` determines which grants reach the entry. Changing it moves the entry between authorization scopes, and is therefore a governance operation (5.4): it MUST be performed only by a Management Client acting for the Authorizing Principal, and MUST be recorded as a `context.recategorized` event naming the prior and new category in detail.
- `record.provenance` sits in `record` because it describes how this HCP Provider received each version, not what an issuer attested. Two providers holding the same credential will hold different provenance for it, and both are correct.

## 4.2.2 Evidence

Each item in `evidence` carries a credential and states its role:

    "evidence": [
      {
        "role": "content | supports",
        "type": "verifiable-credential",
        "credential": { },
        "verification": { "result": "verified | failed", "at": "{ISO-8601}" }
      }
    ]

| Member | Rule |
|-------------|------------------------------------------------------------------|
| `role` | `content`: the credential is the entry's content. `supports`: the credential backs the statement in `content.value`. |
| `type` | The kind of evidence. This draft defines `verifiable-credential`, a complete W3C Verifiable Credential (14). |
| `credential` | The credential, whole, exactly as its issuer secured it |
| `verification` | The HCP Provider's record of its most recent verification of the credential: `result`, `verified` or `failed`, and `at`, when it was established. Set only under the VC Evidence Profile (14.6, 14.8). |

Requirements:

- An entry carries at most one item whose `role` is `content`. Where it carries one, `content` names it (14.2) and carries no `value`.
- The signature boundary: a credential's proof covers that credential and nothing else in the entry. `subject`, `content`, `assertion`, `classification`, `record`, and `verification` are never covered by any proof, and lifecycle changes to them do not invalidate one.
- The HCP Provider MUST NOT alter a credential, or any member of an evidence item other than `verification`.
- The HCP Provider sets `verification` itself. It MUST NOT take it from a request, and MUST NOT emit it for a credential it has not verified.
- An evidence item never raises `assertedBy.assurance` by itself, whatever its `verification` (3.11, invariant 15). An entry is recorded as `cryptographically-verified` only under the VC Evidence Profile, when the credential that is its content passes validation (14.6).
- An HCP Provider that does not conform to the VC Evidence Profile (14) MUST reject a write carrying an evidence item whose `role` is `content`. It MAY accept `supports` items, which it preserves and does not interpret.
- An evidence item of a `type` the HCP Provider does not recognize is preserved and not interpreted (25.3).

Under the VC Evidence Profile, a `supports` credential is verified on ingest and its status kept; a failure is recorded, not rejected (14.8). An HCP Provider that does not conform to that profile records no `verification`.

## 4.2.3 Relationships

`record.relationships` records how an entry relates to other entries held by the same HCP instance.

| Type | Meaning | Effect in this draft |
|----------------|------------------------------------------------------------------|----------------------|
| `derivedFrom` | This entry was inferred or composed from the target | None; informational |
| `supersedes` | This entry replaces the target | The target becomes `deprecated` where a Management Client asserted the relationship, or the target's own Context Asserter did (4.2.4); otherwise none |
| `contradicts` | This entry and the target cannot both be true | The conflict rules in 4.7 |
| `duplicates` | This entry states the same thing as the target | None; informational |

Requirements:

- A relationship is asserted by an HCP Client with a create or revise (5.2.3, 5.2.4), by a Management Client, or by the HCP Provider under the Memory Manager Profile (15). The provider records `assertedBy` (the role, as in 3.9, and identifier of the asserting party) and `recordedAt`. It MUST NOT take either from a request.
- An HCP Client MAY assert a relationship only to an entry in a category its grant authorizes it to read. Any other target fails with not authorized (5.5), without disclosing whether the target exists.
- A `contradicts` relationship is symmetric: the provider records it on both entries.
- When either entry in a `contradicts` relationship is revised, a relationship asserted by an HCP Client is removed unless the revision asserts it again, and a relationship asserted under the Memory Manager Profile is kept only if the provider's method still finds the conflict (15.3).
- A Context Client receives a relationship only where its target is disclosed in the same response, with the target named by its `ref` (7.4). When it asserts a relationship, it names the target by its `ref`.

## 4.2.4 Status

`record.status` is the entry's lifecycle state. A change of status never creates a version (4.2.1).

| Status | Meaning | Entered when | Left when | Context Client |
|------------------------------|-----------------------------------|------------------------------------------------|----------------------------------------|----------------|
| `active` | Current and usable | Created; or returned to by the transitions in 4.7.3 and below | Any other transition | Reads it |
| `deprecated` | Replaced or set aside | A `supersedes` relationship that deprecates it (4.2.3); acceptance of a conflicting entry (4.7.3) | A revision | Cannot read it |
| `conflicted` | Held until the person resolves a conflict | 4.7.2 | 4.7.3 | Cannot read it |
| `expired` | Its content no longer holds | Its `assertion.validUntil`, or its credential's `validUntil` (14.2), has passed | A revision whose validity has not passed | Cannot read it |
| `revoked` | Its content credential's issuer has revoked it | The status of its content credential shows it revoked (14.7) | A revision carrying a new credential | Cannot read it |
| `suspended` | Its content credential's issuer has suspended it | The status of its content credential shows it suspended (14.7) | The issuer lifts the suspension, returning it to the state it held; or a revision carrying a new credential | Cannot read it |
| `deleted` | Withdrawn, and still held | Withdraw (5.2.5); rejection in a conflict (4.7.3) | Hard deletion (5.4.2), which removes the entry | Cannot read it |

- A Context Client reads only `active` entries. A query never returns an entry in another state, and a get entry by `ref` for one MUST fail with not authorized (5.5), exactly as for an entry that does not exist.
- The Context Subject sees entries in every state, through a Management Client and in export (5.4.1).
- `expired` is set lazily, as a grant's expiry is (8.1). The HCP Provider MUST NOT disclose an entry whose validity has passed, whether or not it has set the status yet. It MUST set `expired`, and append a `context.expired` event, no later than the first access to the entry after its validity passes, or within 24 hours of that time, whichever is first.
- `expired` takes precedence over `active`, `deprecated`, `conflicted` and `suspended`; `revoked` over every state but `deleted`; `suspended` over `active`, `deprecated` and `conflicted`; `deleted` over all. A deleted entry is held in full until it is hard-deleted.
- `revoked` and `suspended` are set without delay once the provider establishes the status (14.7), and each change is recorded as a `context.credentialStatus` event (8.1).

## 4.3 One Form, and Conversion from v1

The structure in 4.2 is the only form in which an HCP Provider emits an entry.

- An HCP Provider MUST emit entries only in the form specified in 4.2, with `schema` set as specified there.
- An HCP Provider MAY accept entries written under v1, in v1's grouped form or its flat form, through import only. It MUST declare every entry schema it accepts in its discovery document as `accepts_entry_schemas` (19).
- A context operation (5.2) carrying an entry in any form other than 4.2 MUST be rejected with invalid request (5.5).
- An HCP Provider MUST remain able to read entries in any form it has previously written.

**Conversion from v1.** An HCP Provider that accepts a v1 entry converts it to the form in 4.2:

- Conversion is not a revision. It does not increment `record.version`, does not create a version, and does not append a `context.revised` event.
- Conversion leaves the provenance v1 recorded unaltered, under the mapping below. It adds no confirmation record.
- Every v1 asserter is recorded with assurance `unverified`, because v1 did not record how the asserter was identified. The one exception is an entry whose content is a credential that the provider validates at conversion under the VC Evidence Profile (14.6), which is recorded as `cryptographically-verified`.
- v1's `userVerified` creates no confirmation record and gives the entry no standing in a conflict (4.7.1). A v1 entry that was `user-declared` therefore has no standing until the Context Subject confirms it (3.8).
- The provider records the conversion in `record.conversion`. The Context Subject's own access shows it, and it is withheld from Context Clients (7.4).
- The HCP Provider SHOULD offer the Context Subject, through a Management Client, a way to confirm converted entries whose `record.conversion.unmapped` carries `userVerified: true`. A confirmation so made is an ordinary confirmation record (3.8).

    "conversion": {
      "from": "{v1 entry schema}",
      "convertedAt": "{ISO-8601}",
      "convertedBy": "{provider-identifier}",
      "unmapped": { "userVerified": true }
    }

`unmapped` holds, verbatim, every v1 member that has no place in the form in 4.2.

| v1 field | v2 field |
|-----------------------------------------|------------------------------------------------------------------|
| `credentialType` | Removed. `NLPreference` becomes `content.profile` set to the General Context Profile (11); `VerifiablePreference` becomes an evidence item whose `role` is `content` (14). |
| `claim.subject.id`, `claim.credentialSubject.id` | `subject.id` |
| `claim.subject.preference` | `content.value` |
| `claim.subject.relationship` | `subject.relationship` |
| `claim.issuer`, `claim.issuanceDate` | Removed |
| `claim.expirationDate` | `assertion.validUntil` |
| `record.category`, `record.dimension` | `classification.category`, `classification.dimension` |
| `record.declarationType` | `assertion.declarationType`; `user-declared` becomes `person-declared` |
| `record.confidence` | `assertion.confidence` |
| `record.status`, `record.version` | Unchanged |
| `record.previousVersion` | Removed |
| `record.provenance.capturedBy` | `record.provenance.assertedBy.id`, with assurance as above |
| `record.provenance.capturedAt` | `record.provenance.assertedAt` |
| `record.provenance.source` | Unchanged; `user-input` becomes `person-input` |
| `record.provenance.userVerified` | `record.conversion.unmapped` |

v1 recorded neither the submitting client nor the grant. Where the HCP Provider cannot establish them, it records `submittedByClient` and `authorizedUnder` as the import that carried the entry (5.4.1), and `recordedByProvider` and `recordedAt` as itself and the time of conversion.

## 4.4 Declaration Types

`assertion.declarationType` records what kind of party asserted the content of an entry; `record.provenance.assertedBy.id` records which one (3.5). It is never omitted and never null.

| Value | Meaning |
|---------------------|------------------------------------------------------------------|
| `person-declared` | The Context Subject stated it |
| `model-inferred` | A model derived it from the Context Subject's activity, without the Context Subject having stated it |
| `issuer-attested` | A party other than the Context Subject and other than an inferring model asserted it --- a credential issuer, an institutional integration, or an assessing platform |

- `assertion.confidence` is required and non-null only for `model-inferred` entries. For `issuer-attested` entries the assurance is the proof of a credential that is the entry's content (14), or otherwise the recorded provenance, not a confidence estimate.
- Where `assertion.declarationType` is `model-inferred`, the model is identified as set out in 3.5. A confidence value is not interpretable without knowing what produced it, and a Context Subject deciding whether to accept a quarantined inference (4.7.3) is entitled to know what made it. A `derivedFrom` relationship (4.2.3) can name the entries an inference was drawn from. Richer inference context --- observations that are not entries, and the conditions of their capture --- is deferred (26).
- Confidence is its asserter's own estimate. Values from different asserters are not comparable: `high` from one model and `high` from another say nothing about each other. An HCP Provider MUST NOT use confidence values from different asserters as an input to relevance ordering (7.3) or to standing (4.7.1).
- `issuer-attested` is the expected value for an entry whose content is a credential, but it is not restricted to them. An entry captured from an institutional integration without a credential is `issuer-attested` even though nothing signs it; in that case `record.provenance.source` and `record.provenance.assertedBy` are the only evidence of the assertion, and implementations SHOULD NOT treat it as carrying the assurance a validated credential would.
- A declaration type supplied by a caller does not by itself establish that the Context Subject made the assertion (3.7). Confirmation is recorded separately from declaration type (3.8): a Context Subject can confirm an `issuer-attested` entry is about them without having asserted its content.

**Conflicts involving issuer-attested entries change no status.** An `issuer-attested` claim that contradicts the Context Subject's own declaration is a real and consequential case --- a measured result against what someone says about themselves --- and which should prevail is not obvious. It depends on the domain, on what the claim is being used for, and on how much the Context Subject contests it. A provider is not required to detect these, and a `contradicts` relationship involving one is recorded but quarantines neither entry (4.7); nor is the conflict silently resolved. The case is deferred with the rest of conflict reconciliation (26).

## 4.5 Category Vocabulary

Categories are the primary unit of access control. Every HCP entry belongs to exactly one category. Grants are scoped to categories (6).

The following categories are registered, as version 1 of the category registry (25.1). The registry is versioned separately from this specification, and an implementation declares the registry version it uses in its discovery document as `category_registry` (19). This vocabulary is provisional; it is drawn from the use cases and domains represented at the Global Memory Workshop and has not yet been pressure-tested across sectors. Cross-sector SME engagement is the intended mechanism for expanding and validating it (26).

Implementers may define custom categories. A custom category MUST be an absolute URI under a domain its definer controls, so that two definers cannot collide. Custom categories are not portable across HCP implementations without bilateral agreement.

An HCP Provider MUST reject with invalid request (5.5) a write whose `classification.category` is neither a registered category it holds nor a custom category it supports. It declares both in `supported_categories` (19).

`classification.category` determines which grants reach an entry (4.2.1); a custom category carries no registered default sensitivity, so two implementations cannot agree on what access it implies without agreeing on that out of band.

| Category Slug | Description | Default Sensitivity |
|------------------------------|----------------------------------------------------------|-------------------|
| `general_preferences` | Communication style, formatting, language preferences | Low |
| `goals_and_constraints` | Long-term goals, time constraints, stated priorities | Low |
| `health_context` | Medical conditions, accessibility needs, medications | High |
| `education_learner_profile` | Mastery state, learning preferences, pacing | Medium |
| `work_context` | Role, tools, professional preferences | Medium |
| `purchase_history_preferences` | Shopping preferences, brand affinities | Low |
| `values_and_ethics` | Stated ethical commitments, content boundaries | Medium |
| `location_context` | Geographic preferences and constraints | Medium |
| `coordination_context` | Scheduling rules, availability, relationship constraints | Medium |

Sensitivity levels inform default sharing behavior but do not override the grants the Authorizing Principal has made.

## 4.6 Content Received Before a Grant

Content destined for an HCP instance that arrives before a grant authorizing its handling exists MUST NOT produce an entry, an audit event on the Context Subject's log, or any state visible to a Context Client. It is not yet part of the Context Subject's context. How such content is held, if at all, is outside this specification; the health guide describes one safe pattern (23).

## 4.7 Conflicts

Core defines what happens when two entries conflict. Two entries conflict when a `contradicts` relationship links them (4.2.3), whether an HCP Client, a Management Client, or the HCP Provider asserted it. How a provider finds conflicts itself is defined by the Memory Manager Profile (15). An HCP Provider that accepts `model-inferred` entries MUST conform to the Memory Manager Profile.

The consequences in 4.7.2 apply to a conflict between a `person-declared` entry and a `model-inferred` entry. A `contradicts` relationship between any other pair is recorded and changes no status in this draft. The HCP Provider MUST NOT set `record.status` to `conflicted` on an `issuer-attested` entry (4.4).

### 4.7.1 Standing

Which entry prevails in a conflict is decided by standing, not by declaration type alone. An entry is authoritative if it is a `person-declared` entry recorded as `authenticated` or `cryptographically-verified`, or if the most recent confirmation record on its current version is `confirmed` (3.8).

### 4.7.2 Consequences

However a conflict is asserted, the following are required without variation:

- Where one entry is authoritative and the other is not, the HCP Provider MUST set the entry that is not authoritative to `conflicted`, and the authoritative entry MUST remain active.
- Where neither entry is authoritative --- for instance, an `unverified` `person-declared` entry and a `model-inferred` entry --- the HCP Provider MUST set both to `conflicted`, so that the Context Subject resolves the conflict (3.7).
- The HCP Provider MUST NOT set an authoritative entry to `conflicted`.
- Where both entries are authoritative, this section does not apply. Conflicts between two of the Context Subject's own statements, confirmed or declared, are out of scope, as conflicts between two `person-declared` entries were in v1 (15).
- The HCP Provider MUST append a `conflict.detected` event to the audit log, identifying both entries.
- A conflicted entry MUST NOT be returned to a Context Client in response to a query or a single-entry request. It remains visible to the Context Subject.
- The HCP Provider MUST surface the conflict to the Context Subject through the audit log, and MAY additionally surface it by notification.

### 4.7.3 Resolution

Automated reconciliation is out of scope for this draft (26). Resolution is an act of the Context Subject, performed through a Management Client:

- **Rejecting an entry.** A rejection of the conflicted entry (5.4). The provider appends a `rejected` confirmation record and sets the entry's `record.status` to `deleted`. Where the other entry is `conflicted` and has no other unresolved conflict, the provider MUST return it to `active`. It appends no confirmation record to it, because the person rejected one entry rather than accepting the other. An authoritative entry is unaffected.
- **Accepting an entry.** A confirmation of the conflicted entry (5.4). The provider appends a `confirmed` confirmation record and sets its `record.status` to `active`. Where another entry in the conflict was authoritative, the provider MUST set that entry's `record.status` to `deprecated`. The entry's `declarationType` and `assertedBy` are unchanged (3.8). The prior state remains available through version history.
- **Superseding both.** A revision of the entry the Context Subject wants to keep. The HCP Provider MUST re-evaluate the conflict against the revised entry (4.2.3); where the revision no longer conflicts, any entry quarantined by it MUST return to `active`.

The HCP Provider MUST append a `conflict.resolved` event on any of these transitions.

Where an authoritative entry is deleted while a conflict is outstanding, the conflicted entry MUST remain conflicted. It does not become authoritative by the removal of what it contradicted.
