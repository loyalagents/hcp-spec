# 5. Operations and Errors

## 5.1 Operations

HCP supports five operations on entries for HCP Clients acting under a grant, and a set of governance operations for the Authorizing Principal. Any conformant system --- an AI assistant, a healthcare portal, an education platform --- interacts with an HCP instance through exactly these operations, and only under the access the Authorizing Principal has explicitly granted.

| Operation | Plane (2.6) | In plain language | Section |
|--------------------------|------------|-----------------------------------------------------------------|---------|
| Query | Context | Retrieve entries relevant to a query. Only entries in authorized categories are returned, filtered to the minimum necessary for the stated purpose. | 5.2.1 |
| Get entry | Context | Retrieve one named entry, for a stated purpose. | 5.2.2 |
| Create | Context | Create a new entry. Its provenance is recorded automatically (3.5). | 5.2.3 |
| Revise | Context | Create a new version of an entry. The prior version is never deleted; it is versioned. | 5.2.4 |
| Withdraw | Context | Mark an entry as deleted (soft delete). | 5.2.5 |
| Read own grant | Context | An HCP Client reads the grant under which it acts. | 5.2.6 |
| Relinquish own grant | Context | An HCP Client gives up the grant under which it acts. | 5.2.7 |
| Governance operations | Governance | List and revoke grants, read the audit log and the disclosure summary, export and import, hard delete, confirm or reject an entry, change an entry's category, set and remove standing rules. | 5.4 |

Core defines one request and one result for each operation below. A binding MAY expose a subset of an operation's fields; it MUST NOT give any field a different meaning (2.5).

No operations on stored entries other than the context operations are available to a Context Client. Context Client access is always query-scoped and minimized; bulk retrieval of a Context Subject's entries by a Context Client is not supported. The Context Subject's own export of their data (5.4) is a governance operation and is not restricted by this section.

## 5.2 Context Operations

### 5.2.1 Query

| Request field | Required | Description |
|------------------|-------------|------------------------------------------------------------------|
| `query` | Yes | Natural language query describing the context or task |
| `categories` | No | Categories to query. Omitted means every category the grant can read for the purpose named. |
| `purpose` | Yes | A purpose code: one the grant approved for the categories queried (6.1.5.2) |
| `purposeDescription` | No | Plain language statement of the task. Recorded in the audit log. |
| `maxEntries` | No | Maximum entries to return. Default 5; subject to the ceiling in 7.2. |

| Result field | Description |
|----------------------|------------------------------------------------------------------|
| `entries` | The entries returned, in relevance order (7.3): disclosures where the requester is a Context Client (7.4) |
| `retrievalId` | `urn:uuid:` identifier of this retrieval, recorded in the audit event |
| `minimization` | The minimization report (7.5) |
| `categoriesSearched` | The categories searched: those named in the request, or, where it named none, every category the grant can read for the purpose named |
| `timestamp` | ISO-8601 time of the response |

A query naming any category outside the grant's scopes, or a purpose the grant did not approve for those categories, MUST fail with not authorized (5.5). Query results are not paginated (7.2). Both bindings return `categoriesSearched`.

### 5.2.2 Get Entry

Retrieves a single entry. A Context Client names it by the `ref` it was disclosed with (7.4); a Management Client by its `id`.

| Request field | Required | Description |
|------------------|-------------|------------------------------------------------------------------|
| `ref` or `entryId` | Yes, one of them | The entry's `ref` (a Context Client) or its `id` (a Management Client) |
| `purpose` | Yes | A purpose code: one the grant approved for the entry's category (6.1.5.2) |
| `purposeDescription` | No | Plain language statement of the task. Recorded in the audit log. |
| `version` | No | Integer. Returns the specified version rather than the current one. |

| Result field | Description |
|----------------------|------------------------------------------------------------------|
| `entry` | The entry: a disclosure where the requester is a Context Client (7.4) |
| `retrievalId` | `urn:uuid:` identifier of this retrieval |
| `minimization` | The minimization report (7.5) |
| `timestamp` | ISO-8601 time of the response |

Requirements:

- The entry's `classification.category` MUST be within the caller's authorized scopes, and `purpose` MUST be among those the grant approved for that category (6.1.5.2).
- The HCP Provider MUST append a `context.read` event identical in structure to the event appended for a query, including the stated purpose.
- A Context Client receives a disclosure (7.4), with its use-until time (7.6), as for a query.
- Entry-selection minimization under 7 is inapplicable by construction, since the caller has named a single entry. Conformance testing MUST NOT treat the absence of entry-selection filtering on this operation as non-conformance.
- A Context Client can name only entries disclosed to it under the same grant, since it knows no other `ref`.
- A request for an entry that does not exist, that is outside the caller's authorized scopes, whose `ref` belongs to another grant, or that is not `active` (4.2.4), MUST fail with not authorized (5.5), so that entry existence is not disclosed to unauthorized callers.

The entry is returned inside a result rather than bare, so that the minimization report required by 7.5 has somewhere to sit.

### 5.2.3 Create

| Request field | Required | Description |
|------------------------------|-------------|------------------------------------------------------------------|
| `schema` | Yes | The entry structure version (4.2) |
| `subject.id` | Yes | The Context Subject (4.2) |
| `content` | Yes | The content, in the shape its profile defines (11, 14) |
| `evidence` | No | Evidence items (4.2.2) |
| `classification.category` | Yes | Category slug or custom category URI (4.5) |
| `assertion.declarationType` | Yes | `person-declared`, `model-inferred`, or `issuer-attested` (4.4) |
| `classification.dimension` | No | Dimension within the category (4.2) |
| `assertion.confidence` | Conditional | Required and non-null when `declarationType` is `model-inferred`; null or omitted otherwise |
| `assertion.validUntil` | No | When the content stops holding (4.2) |
| `record.provenance.assertedBy.id` | Conditional | The Context Asserter. Required unless `declarationType` is `person-declared`, in which case the provider records the Context Subject, or the entry's content is a credential, in which case the provider takes it from the credential's issuer (14.6). |
| `record.provenance.assertedAt` | No | When the assertion was made. Omitted means the provider records `recordedAt`. |
| `record.provenance.source` | Yes | Origin of the entry |
| `relationships` | No | Relationships to assert, each a `type` and a `target`: the target's `ref` for a Context Client, its `id` for a Management Client (4.2.3) |

The HCP Provider assigns everything else:

| Field | Assigned by |
|-------------------------------------------|---------------------------------------------------------|
| `id` | HCP Provider |
| `record.status` | HCP Provider |
| `record.version` | HCP Provider |
| `record.provenance.assertedBy.assurance`, `submittedByClient`, `authorizedUnder`, `recordedByProvider`, `recordedAt`, `confirmations` | HCP Provider (3.5) |
| `record.relationships[].assertedBy`, `recordedAt` | HCP Provider (4.2.3) |

Requirements:

- A write that omits or nulls `confidence` while declaring `model-inferred` MUST be rejected with invalid request (5.5). A write that supplies a non-null `confidence` while declaring anything other than `model-inferred` MUST be rejected the same way.
- A write naming a `schema` the HCP Provider does not accept, or a category it does not hold, MUST be rejected with invalid request (4.2, 4.5).
- An `issuer-attested` write is accepted only from an HCP Client authenticated as the issuer, or authorized by it; any other is rejected with not authorized (3.7). A write whose content is a credential is `issuer-attested`.
- Where the content is a credential, the client supplies it whole, including its proof, in an evidence item, and the HCP Provider MUST NOT modify it (4.2.2).

Result: the created entry with provider-assigned fields populated, as a disclosure carrying its new `ref` where the requester is a Context Client (7.4).

### 5.2.4 Revise

| Request field | Required | Description |
|--------------------------|-------------|------------------------------------------------------------------|
| `ref` or `entryId` | Yes, one of them | The entry to revise, named as for get entry (5.2.2) |
| `expectedVersion` | Yes | The `record.version` of the current version, which this revision replaces |
| `content` | Yes | The revised content, whole. Where the content is a credential, the new credential, whole, in `evidence`. |
| `evidence` | No | The revision's evidence items, whole (4.2.2). Omitted means none. |
| `reason` | Yes | Reason for the revision. Recorded in the audit log. |
| `assertion.declarationType` | No | The declaration type of the revised assertion. Omitted means unchanged. |
| `assertion.confidence`, `assertion.validUntil` | Conditional | As for create |
| `record.provenance.assertedBy.id`, `assertedAt`, `source` | Conditional | As for create, for the revised assertion |
| `relationships` | No | As for create (4.2.3) |

A revision creates a new version. It replaces `content`, `assertion`, and `evidence` whole; `subject` and `classification` are not changed by a revision (4.2.1). Its provenance belongs to the new version and is recorded as for create (3.5): the revised assertion is attributed to its own Context Asserter, and the new version starts with no confirmations (3.8).

Where `expectedVersion` is not the entry's current `record.version`, the revision MUST fail with version conflict (5.5) and change nothing. Revisions are therefore never lost to a concurrent one: a client that read version 4 cannot overwrite a version 5 it has not seen.

Result: the revised entry, with `record.version` incremented by 1, as a disclosure where the requester is a Context Client (7.4). The entry's `id`, and its `ref` under the grant, are unchanged by a revision.

A Context Client MUST NOT revise an entry whose current version the Context Subject has rejected (3.8).

### 5.2.5 Withdraw

| Request field | Required | Description |
|------------------|-------------|------------------------------------------------------------------|
| `ref` or `entryId` | Yes, one of them | The entry to withdraw, named as for get entry (5.2.2) |
| `reason` | Yes | Reason for withdrawal. Recorded in the audit log. |

Withdraw sets the entry's `record.status` to `deleted`. A deleted entry is hidden from Context Clients immediately. It remains held, and remains visible to the Context Subject, until hard-deleted (5.4).

Result: the `ref` or `entryId` named, `status` (`deleted`), and `timestamp`.

### 5.2.6 Read Own Grant

An HCP Client MAY read the grant under which it acts (6.1.5). It receives that grant only. Where the grant is narrowed to particular entries (6.1.5.1), a Context Client receives their `ref`s, never their `id`s. Reading it discloses nothing the client was not already told at authorization time, and no audit event is required.

### 5.2.7 Relinquish Own Grant

An HCP Client MAY relinquish the grant under which it acts. Relinquishing is a revocation of that grant: it takes effect as 6.2.2 requires and is recorded as a `grant.revoked` event naming the client as initiator (3.9). No revocation notification is sent to the client that relinquished the grant.

A client can relinquish only the grant it presents. A request naming any other grant MUST fail with not authorized (5.5). Revoking any other grant remains a governance operation (5.4, 6.2.1).

The HTTP Binding carries this operation (9.4.6). The MCP Binding does not carry it in this draft.

## 5.3 Minimal Response Mode (Removed)

Draft 1 let a query ask for a `minimal` response, which reduced each General Context entry to its identifier, category, dimension, and value. A Context Client now always receives disclosures (7.4), which carry no provenance or lifecycle fields beyond what judging standing requires. The section number is kept so that citations of it resolve.

## 5.4 Governance Operations

Governance operations are performed only by a Management Client acting for the Authorizing Principal (6.1.9), and are carried only by the HTTP Binding (2.6, 9). The audit events they produce are listed in 8.1.

| Operation | Effect | Section |
|-------------------------|------------------------------------------------------------------|---------|
| List grants | Enumerates all grants for the instance, filtered by status if asked | 6.1.5 |
| Revoke grant | Revokes a grant | 6.2 |
| Read audit log | Returns the audit log, filtered as asked | 8.3 |
| Export | Returns the Context Subject's entries | 5.4.1 |
| Import | Loads entries from an export, at the Context Subject's direction | 5.4.3 |
| Disclosure summary | Summarizes what each client has received | 8.6 |
| Hard delete | Permanently removes an entry | 5.4.2 |
| Confirm or reject | Appends a confirmation record to an entry's current version | 3.8, 4.7.3 |
| Change category | Moves an entry to another category | 4.2.1 |
| Set or remove a standing rule | Denies context to named Client Operators, across all categories or within some | 6.3 |

Confirm or reject, and change category, MUST carry `expectedVersion`, the `record.version` the Management Client showed the Context Subject. Where it is not the entry's current version, the operation MUST fail with version conflict (5.5) and change nothing, so that a person never confirms, rejects, or recategorizes a version they have not seen.

### 5.4.1 Export

**Default content.** The current version of every entry across all categories that has not been hard-deleted, as a JSON-LD document. This includes entries whose `record.status` is `active`, `deprecated`, `conflicted`, `expired`, `revoked`, `suspended`, or `deleted`. Every entry carries its status. The export also carries the Context Subject's standing rules (6.3).

The default follows one principle: **the export contains anything whose existence the Context Subject could not otherwise infer from it.** A soft-deleted entry is still held and still processed, and a person reading a filtered export has no way to discover that it exists --- they cannot ask for what they do not know is there. A superseded version, by contrast, is announced by the current entry's `record.version`, and the audit log is separately available (8.3). Both are therefore opt-in.

An export request MAY ask for:

- **Excluding deleted entries.** Omits entries whose `record.status` is `deleted`. Intended for a Context Subject preparing to move their context to another provider, where entries they have deleted should not travel with it.
- **Including versions.** Additionally returns superseded versions of each entry returned, rather than the current version alone.
- **Including the audit log.** Additionally returns the Context Subject's audit log in the structure specified in 8.2. This is equivalent to the export already required by 8.3 and is offered as a convenience, not as an additional capability.

Entries removed by hard deletion are by definition unrecoverable and MUST NOT be returned under any option.

The HCP Provider MUST append a `context.exported` event for every export, recording the options used in detail.

### 5.4.2 Hard Deletion

Implementations MUST support hard deletion at the Context Subject's request, to support applicable erasure and deletion obligations. Hard deletion is a governance operation: a Context Client cannot perform it, and an attempt by any caller other than a Management Client acting for the Authorizing Principal MUST fail with not authorized (5.5). A Context Client can only withdraw (5.2.5), which hides the entry from Context Clients immediately.

### 5.4.3 Import

Import loads the entries of an HCP export (5.4.1) into the Context Subject's instance, at their direction, through a Management Client. It is not federation: one person moves their own context (26).

| Request field | Required | Description |
|------------------|-------------|------------------------------------------------------------------|
| `export` | Yes | An HCP export, with entries in any schema the provider accepts (4.3) |
| `dryRun` | No | If true, report the outcome for each entry and change nothing |
| `categoryMap` | No | For entries in categories the provider does not hold: the category each is to be placed in |

Result: one outcome for each entry in the export: `imported`, `converted` (a v1 entry, converted under 4.3), `skipped` (a deleted entry the request chose not to carry, or an exact duplicate of one held), or `rejected`, with the reason.

Requirements:

- An implementation that imports v1 entries converts them as 4.3 requires.
- An entry whose `id` is already held, with different content, MUST be rejected. It is never overwritten.
- The HCP Provider MUST NOT reinstate as active any entry carrying `record.status: deleted`. It either preserves the status or omits the entry. The safeguard against deleted context resurfacing at another provider belongs on the reading side, not in what a person is permitted to see of their own data.
- The HCP Provider MUST preserve each entry's `assertion.declarationType` and `record.provenance`, including its confirmation records, as exported. Assurance values remain the exporting provider's record, which `recordedByProvider` shows. Nothing is upgraded (3.11, invariant 15).
- An entry whose content is a credential is verified again under the VC Evidence Profile, with its status (14.6, 14.7). One that fails is rejected as credential invalid (5.5). A supporting credential is verified again and its `verification` recorded anew (14.8).
- The HCP Provider MUST NOT silently re-categorize an imported entry: because `classification.category` governs which grants reach the entry (4.2.1), assigning a different category on import changes what the Authorizing Principal's existing and future grants mean. An entry in a category the provider does not hold is rejected, unless `categoryMap` places it. Each placement is recorded as a `context.recategorized` event naming the prior and new category, exactly as for any other change of category (4.2.1).
- Standing rules in the export are applied as the Context Subject's own (6.3).
- The HCP Provider MUST append one `context.imported` event for each import other than a dry run, listing the entries and their outcomes (8.1).

## 5.5 Errors

Core defines the following errors. Each has a code, which bindings carry: the HTTP Binding as a problem type (9.7), the MCP Binding in a tool execution error (10.4). The codes are v1's problem-type names, with `version-conflict` and `credential-invalid` added in this draft.

| Error | Code | Condition |
|-----------------------|------------------------|------------------------------------------------------------------|
| invalid request | `malformed-request` | The request fails schema validation or a Core rule on its content |
| unauthenticated | `invalid-token` | Missing, malformed, or expired authorization evidence |
| not authorized | `scope-denied` | The request falls outside the caller's grant --- its categories, actions, or purposes --- or the entry does not exist. The response MUST NOT disclose which. |
| conflict | `idempotency-conflict` | A retried request does not match the original (9.6) |
| version conflict | `version-conflict` | The request names a version that is not the entry's current version (5.2.4, 5.4) |
| credential invalid | `credential-invalid` | A credential that is an entry's content fails verification: its proof, its securing mechanism, its verification method, or its status (14.6). The detail names which, and does not reveal status-list internals. |
| rate limited | `rate-limited` | The caller has exceeded a rate limit. Revocation is never rate limited (6.2.1). |
| unsupported version | `unsupported-version` | The requested protocol version is not supported. The HCP Provider MUST NOT silently serve a different version. |
