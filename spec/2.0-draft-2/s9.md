# Part II --- Bindings

# 9. HTTP Binding

## 9.1 Scope

This section maps the Core operations (5) and errors (5.5) onto HTTP. It is identified as https://hcp.example/spec/bindings/http/2.0 (2.7).

The HTTP Binding exists for traditional, auditable server-to-server integration --- institutional systems, batch jobs, and clients that are not LLM-mediated --- where a conventional HTTP client is the natural fit; the MCP Binding (10) exists for agent-native access, where an LLM discovers and invokes tools directly. The HTTP Binding is also the only binding that carries governance operations (2.6), and it is required for the Provider Interop package (18).

The base URL is implementation-defined. An implementation exposing the HTTP Binding MUST publish a discovery document at `/.well-known/hcp-configuration` (19).

## 9.2 Endpoints

| Core operation | Plane | Method | Path |
|-----------------------------------|------------|--------|------------------------------------------------|
| Query (5.2.1) | Context | POST | `/v2/entries/query` |
| Get entry (5.2.2) | Context | GET | `/v2/entries/{entryId}` |
| Create (5.2.3) | Context | POST | `/v2/entries` |
| Revise (5.2.4) | Context | POST | `/v2/entries/{entryId}/revisions` |
| Withdraw (5.2.5) | Context | DELETE | `/v2/entries/{entryId}` |
| Read own grant (5.2.6) | Context | GET | `/v2/grants`, with a Context Client's token |
| List grants (5.4) | Governance | GET | `/v2/grants`, with a Management Client's token |
| Relinquish own grant (5.2.7) | Context | DELETE | `/v2/grants/{grantId}`, with a Context Client's token for that grant |
| Revoke grant (6.2) | Governance | DELETE | `/v2/grants/{grantId}`, with a Management Client's token |
| Read audit log (8.3) | Governance | GET | `/v2/audit` |
| Export (5.4.1) | Governance | GET | `/v2/export` |
| Hard delete (5.4.2) | Governance | DELETE | `/v2/entries/{entryId}?hardDelete=true` |
| Confirm or reject (3.8) | Governance | POST | `/v2/entries/{entryId}/confirmation` |
| Change category (4.2.1) | Governance | PUT | `/v2/entries/{entryId}/category` |
| Import (5.4.3) | Governance | POST | `/v2/import` |
| Disclosure summary (8.6) | Governance | GET | `/v2/disclosures` |
| List delegations (17.2) | Governance | GET | `/v2/delegations` |
| List or set standing rules (6.3) | Governance | GET, POST | `/v2/rules` |
| Remove standing rule (6.3) | Governance | DELETE | `/v2/rules/{ruleId}` |
| Relinquish or end delegation (17.6) | Governance | DELETE | `/v2/delegations/{delegationId}`, with a delegate's Management Client token, or the Context Subject's for an appointed delegation |

Where the caller is a Context Client, `{entryId}` in a path is the entry's `ref` (7.4).

A request to a governance endpoint from anything other than a Management Client acting for the Authorizing Principal, or under the Delegated Authorization Profile for the Context Subject or a delegate (17), MUST fail with not authorized (6.1.9).

## 9.3 General Requirements

All requests MUST include a Bearer token in the Authorization header. Successful responses are `application/ld+json`. Error responses are `application/problem+json` (9.7).

**Protocol version.** Every response, including error responses and responses with no body, MUST carry an `HCP-Version` header whose value matches the `hcp_version` published in the implementation's discovery document. Responses do not carry an `hcp_version` member in the body.

Clients MAY send an `HCP-Version` request header naming the protocol version they expect. An implementation that does not support the requested version MUST respond with unsupported version (9.7), and MUST NOT silently serve a different version.

## 9.4 Operations

### 9.4.1 Query

`POST /v2/entries/query`. The request body carries the fields in 5.2.1:

    {
      "query": "footwear constraints for hiking",
      "categories": ["health_context"],
      "purpose": "https://purposes.example/product-recommendation",
      "purposeDescription": "Choosing hiking boots",
      "maxEntries": 5
    }

`maxEntries` defaults to 5 and is subject to the ceiling in 7.2.

Response (200):

    {
      "entries": [ ],
      "retrievalId": "urn:uuid:{uuid}",
      "minimization": { "method": "lexical" },
      "categoriesSearched": ["health_context"],
      "timestamp": "{ISO-8601}"
    }

Each item in `entries` is a disclosure where the caller is a Context Client (7.4); 9.4.2 shows one.

### 9.4.2 Get Entry

`GET /v2/entries/{entryId}`, with the query parameters `purpose` (required, a purpose code), `purposeDescription` (optional), and `version` (optional), as defined in 5.2.2. Where the caller is a Context Client, the path segment is the entry's `ref` (7.4); for a Management Client it is the entry's `id`. The same holds for every path below that names an entry.

Response (200), shown for a General Context entry disclosed to a Context Client (7.4):

    {
      "entry": {
        "ref": "r_8Jq2vNw4TzL0",
        "version": 2,
        "content": {
          "profile": "https://hcp.example/spec/profiles/general-context/2.0",
          "value": "I need wide-toe-box shoes with arch support."
        },
        "evidence": [],
        "assertion": { "declarationType": "person-declared", "confidence": null, "validUntil": null },
        "classification": { "category": "health_context", "dimension": "footwear_support" },
        "standing": { "assurance": "authenticated", "confirmed": false },
        "useUntil": "2026-10-27T14:02:12Z"
      },
      "retrievalId": "urn:uuid:{uuid}",
      "minimization": { "method": "none" },
      "timestamp": "{ISO-8601}"
    }

`health_context` has a default sensitivity of High, so this copy is usable for at most 24 hours (7.6).

### 9.4.3 Create

`POST /v2/entries`. The request body is an entry in the form specified in 4.2, carrying the request fields in 5.2.3 and omitting the fields the HCP Provider assigns. Response (201): the created entry with provider-assigned fields populated.

### 9.4.4 Revise

`POST /v2/entries/{entryId}/revisions`. A revision is a new version, created as a subordinate resource of the entry. Request body:

    {
      "expectedVersion": 2,
      "content": {
        "profile": "https://hcp.example/spec/profiles/general-context/2.0",
        "value": "I require high arch support and wide toe box in footwear.",
        "language": "en"
      },
      "reason": "Correction by the Context Subject during conversation"
    }

The body MAY also carry the optional fields in 5.2.4. Response (201): the revised entry, with `record.version` incremented by 1. The entry's `id` is unchanged by a revision. Where `expectedVersion` is not the current version, the response is version conflict (9.7).

### 9.4.5 Withdraw and Hard Delete

`DELETE /v2/entries/{entryId}` withdraws an entry (5.2.5). With the query parameter `hardDelete=true` it hard-deletes the entry instead (5.4.2), which only a Management Client may do (6.1.9).

Response (200):

    {
      "entryId": "urn:uuid:{uuid}",
      "status": "deleted",
      "hardDeleted": false,
      "timestamp": "{ISO-8601}"
    }

### 9.4.6 Grants

`GET /v2/grants` returns grant objects (6.1.5). Access is scoped by caller:

- Called by a Management Client acting for the Authorizing Principal, it returns all grants. An optional `status` query parameter filters by status; the default is `active`.
- Called with a Context Client's bearer token, it returns only the grant under which that token was issued.

Responses MAY be paginated per 9.5.

`DELETE /v2/grants/{grantId}` revokes a grant (6.2). Called by a Management Client, it revokes any grant for the instance. Called with a Context Client's bearer token, it relinquishes the grant under which that token was issued (5.2.7); naming any other grant fails with not authorized.

### 9.4.7 Audit Log

`GET /v2/audit` returns the audit log (8.3). It MUST support cursor-based pagination (9.5).

### 9.4.8 Export

`GET /v2/export` returns an export (5.4.1). The export options map to query parameters:

| Parameter | Required | Values | Export option (5.4.1) |
|-----------|----------|----------------------------------|----------------------------------|
| `include` | Optional | Comma-separated: `audit`, `versions` | Including the audit log; including versions |
| `exclude` | Optional | Comma-separated: `deleted` | Excluding deleted entries |

The `context.exported` event records the parameters used in detail.

### 9.4.9 Confirm or Reject

`POST /v2/entries/{entryId}/confirmation`. Request body:

    { "disposition": "confirmed | rejected", "expectedVersion": 2 }

The HCP Provider appends the confirmation record to the entry's current version (3.8) and applies the status transitions in 4.7.3. Response (200): the entry.

### 9.4.10 Change Category

`PUT /v2/entries/{entryId}/category`. Request body:

    { "category": "{category-slug}", "expectedVersion": 2 }

Response (200): the entry, with the new category. The change is recorded as in 4.2.1.

### 9.4.11 Import

`POST /v2/import`. The request body carries the fields in 5.4.3:

    {
      "export": { },
      "dryRun": true,
      "categoryMap": { "https://categories.example/fitness": "general_preferences" }
    }

Response (200): one outcome per entry.

    {
      "outcomes": [
        { "id": "urn:uuid:{uuid}", "outcome": "converted" },
        { "id": "urn:uuid:{uuid}", "outcome": "rejected", "reason": "id held with different content" }
      ],
      "dryRun": true
    }

### 9.4.12 Disclosure Summary

`GET /v2/disclosures`, with the optional query parameters `client`, `category`, `from`, and `to`. Response (200): a `clients` array, one member per HCP Client, each carrying the members in 8.6. It MAY be paginated per 9.5.

### 9.4.13 Delegations

An implementation conforming to the Delegated Authorization Profile (17) exposes:

- `GET /v2/delegations`. Response (200): a `delegations` array of delegation objects (17.2), with ended ones where `status=ended` is asked. A Management Client acting for the Context Subject receives every delegation for them; one acting for a delegate receives only the delegations naming that delegate.
- `DELETE /v2/delegations/{delegationId}`, by a Management Client acting for the delegate it names: relinquishes the delegation (17.6). Where the delegation's basis is `appointed`, a Management Client acting for the Context Subject may also call it, which ends the delegation with reason `ended-by-subject`. Response (204). Any other caller receives not authorized.

A delegation is established by the Authorization Service, not through this binding (17.2).

### 9.4.14 Standing Rules

- `GET /v2/rules`. Response (200): a `rules` array of standing rules (6.3).
- `POST /v2/rules`, with `operators` and, optionally, `categories`. Response (201): the rule, with its `ruleId` and `createdAt`. The HCP Provider sets `effect` to `deny`.
- `DELETE /v2/rules/{ruleId}`. Response (204).

Each is called by a Management Client acting for the Context Subject, or, under the Delegated Authorization Profile, for a delegate within the delegation's scope (6.3). A delegate's `DELETE` succeeds only for a rule they set. Any other caller receives not authorized.

## 9.5 Pagination

`GET /v2/audit` MUST support cursor-based pagination:

| Parameter | Location | Description |
|-----------|-----------------|------------------------------------------------|
| `cursor` | Query, optional | Opaque continuation token from a prior response |
| `limit` | Query, optional | Maximum events in this page |

Responses carry a `nextCursor` member holding an opaque token, or null when the result set is exhausted. Cursors MUST be opaque to clients, MUST NOT encode credentials or entry content, and MUST remain valid for at least 300 seconds.

A bare sequence number or offset does not satisfy the opacity requirement. A pilot implementer asked whether a plain incrementing integer may serve as a cursor (Turn.io); it may not, because a monotonic cursor discloses the total number of audit events to any client that receives one, which is itself information about the volume of a person's activity. An opaque cursor may be an encrypted or signed offset, or a server-side handle; what it MUST NOT be is a value from which a client can read the size or position of the underlying set.

`POST /v2/entries/query` is not paginated (7.2).

## 9.6 Idempotency

`POST /v2/entries` and `POST /v2/entries/{entryId}/revisions` MUST accept an `Idempotency-Key` request header, and clients SHOULD send one.

- Implementations MUST retain a key and its associated response for at least 24 hours.
- A repeated request bearing a previously seen key and an identical body MUST return the original response --- including the original entry `id` and `record.version` --- without performing the operation a second time.
- A repeated key accompanied by a differing body MUST be rejected with conflict (9.7).
- A replayed request MUST NOT append a second audit event.

`DELETE /v2/entries/{entryId}` SHOULD accept the header. Repeated deletion is harmless to entry state but appends a duplicate audit event without it.

A revision needs a key as much as a create. Without one, a retried revision whose first attempt succeeded fails with version conflict (5.2.4), and the client cannot tell its own success from someone else's revision.

## 9.7 Errors

All error responses MUST use `application/problem+json` per RFC 9457, carrying at minimum `type`, `title`, `status`, and `detail`. Implementations MAY add extension members.

Each Core error (5.5) maps to one status. Its problem type is its code, relative to https://hcp.example/problems/:

| Core error (5.5) | Status | Problem type |
|-----------------------|--------|------------------------|
| invalid request | 422 | `malformed-request` |
| unauthenticated | 401 | `invalid-token` |
| not authorized | 403 | `scope-denied` |
| conflict | 409 | `idempotency-conflict` |
| version conflict | 409 | `version-conflict` |
| credential invalid | 422 | `credential-invalid` |
| rate limited | 429 | `rate-limited` |
| unsupported version | 400 | `unsupported-version` |

A `scope-denied` response MUST NOT disclose whether the requested entry exists (5.2.2).

## 9.8 Rate Limiting

A 429 response MUST include a `Retry-After` header. Implementations SHOULD publish their rate limit policy in the discovery document (19).

Rate limiting MUST NOT be applied to `DELETE /v2/grants/{grantId}` (6.2.1).

## 9.9 Revocation Notification Delivery

Where an HCP Client has registered a notification endpoint, the notification required by 6.2.2 is a Security Event Token (SET, RFC 8417), delivered to that endpoint by push delivery (RFC 8935).

**The token.** The SET carries:

    {
      "iss": "https://provider.example",
      "aud": "{client-identifier}",
      "jti": "urn:uuid:{event-uuid}",
      "iat": 1761537600,
      "events": {
        "https://hcp.example/spec/events/grant-revoked": {
          "grantId": "urn:uuid:{grant-uuid}",
          "revokedAt": "{ISO-8601}"
        }
      }
    }

- `iss` is the HCP Provider, `aud` the HCP Client being notified, and `iat` the time the token was issued.
- `jti` identifies the notification. It is identical on every delivery attempt, and receiving clients use it to deduplicate.
- The event type is `https://hcp.example/spec/events/grant-revoked`. It names the grant revoked and when.

**Signing.** The SET MUST be signed with JWS using an asymmetric algorithm, with a key published in the JSON Web Key Set at the discovery document's `jwks_uri` (19). Receiving clients MUST verify the signature, and SHOULD reject a token whose `iat` differs from local time by more than 300 seconds.

**Delivery.** Delivery is an HTTP POST of the SET, with media type `application/secevent+jwt`, as RFC 8935 specifies. The client acknowledges receipt with 202 Accepted, or rejects the token with 400 and an RFC 8935 error code.

**Retry.** Delivery MUST be retried on connection failure and on any response other than 202 or 400, with exponential backoff, for at least 5 attempts over at least 1 hour before delivery is abandoned. Every attempt MUST carry the same token. A 400 response ends delivery and is recorded as abandoned, with the client's error code.

Auditing, abuse controls, and independence from revocation are Core requirements (6.2.3, 6.2.4).
