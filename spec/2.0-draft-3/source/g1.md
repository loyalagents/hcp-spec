# Guides

Δ MOVED (v2-draft-3) --- Draft 2's Part V, §21--24, becomes the Guides page, G1--G4; G5 is new (RS1, RS2).

These guides are non-normative (1.2). Nothing in them is a requirement of this specification. Where a guide relies on a rule, it cites the Part that states it, and that statement governs.

HCP is a protocol, not a user experience pattern. How applications elicit context from people --- onboarding interviews, reflective dialogue, passive capture --- is outside this specification, and pilot teams should treat elicitation design as an implementation choice. Authorization interaction is different in kind: it is where consent is constituted, and 6.1.4 places requirements on it. The patterns in G4 illustrate those requirements; they do not extend them, and they say nothing about elicitation.

# G1. Pilot Onboarding

## G1.1 Recommended Sequence

**Availability.** This repository does not currently designate a validated Draft 3 reference implementation or publish the behavioral suite named below. See the [artifact status](https://github.com/loyalagents/hcp-spec#drafts-and-available-artifacts) for available examples and implementation projects. Schema/example checks alone do not establish implementation conformance.

1. Stand up an HCP Provider: the reference implementation or a conformant third-party implementation.
2. Choose a package (18.2). If every HCP Client the pilot uses is operated by the Provider Operator, the First-Party package is available. If any client is operated by another organization, Provider Interop is required (18.3).
3. Register each HCP Client, identifying its Client Operator by an identifier and a name the person can recognize (3.2.8).
4. Define the category scopes the pilot needs (6.1.1).
5. Implement the bindings the package requires: the HTTP Binding, the MCP Binding, or both. MCP over stdio qualifies for First-Party only (10.1).
6. If the pilot will accept `model-inferred` entries, implement the Memory Manager Profile (4.7, 15).
7. Run the conformance test suite (20).
8. Walk pilot participants through the authorization flow before data collection begins (G4).

## G1.2 What Pilots Should Record

Δ CHANGED (v2-draft-3) --- Pilots also report proposals accepted and how long conflicts stayed open (M8). End-to-end pilots report how often the trust domain was unreachable (ST6).

Several decisions in this specification are waiting on pilot evidence (P1). Pilots can supply it by recording the following:

- **Which evidence the pilot tests.** Name the rung: protocol conformance (20); context quality, such as necessary against excessive disclosure, staleness and correction; task performance against a realistic baseline; outcomes for people; or institutional readiness. Passing conformance tests does not show that disclosed context was appropriate or that it helped anyone, and a pilot that tests one rung should not claim the next.
- **Shared measures for people.** So that pilots can be compared, record where you can: whether people repeat themselves less across AI applications, and how much setup time is saved; whether responses are more relevant; whether people understand what is held, who can see it, and how to correct or revoke it; whether they can find and fix inaccurate or outdated entries; and whether their trust changes. Compare against a simpler alternative, such as copying preferences between assistants by hand. Where possible, keep a replayable test: the same request answered with and without HCP context, to show whether the context changed the answer.
- **Audit volume.** How much storage the audit log used, and how much of it was `context.read` events (8.1). One implementer of Draft 1 found read logging grew to several times the size of everything else held. Evidence of the cost is the input to any change in what read events record (P1).

- **Custom categories.** Where a needed category is missing, define it as a URI under a domain you control (4.5), document the category, and submit it for the vocabulary review.
- **Facets or categories.** Whether record or document types were distinguished as facets within an entry or as separate categories, and where people wanted finer control than a category gave them. Both approaches are conformant.
- **Dimension values.** The `classification.dimension` values the pilot used (4.2). No vocabulary is registered, and the values pilots adopt are the best evidence for one.
- **Use-until.** How long clients needed disclosed copies, and whether the floor of 1 hour and the ceilings of 30 days and 24 hours (7.6) were too short or too long.
- **Conflicts.** How often conflicts arose, between which kinds of entry, and how people resolved them (4.7.3); how often they accepted a proposal (4.7.4); and how long conflicts stayed open. This is the input to automated resolution (P1).
- **Residency.** Where context had to be stored and processed in a jurisdiction, and how the pilot met it (G3.7).
- **Storage.** Whether the pilot's storage is end-to-end encrypted (4.8), and if so how often the trust-domain component could not be reached when a request needed it, and how long requests waited.

## G1.3 On-Device and Operator-Blind Deployments

Δ CHANGED (v2-draft-3) --- End-to-end encrypted storage is no longer open (ST1).

Core governs behavior at the interface boundary, not internal storage (Part I). A deployment that runs models on the person's device, or splits processing between device and server, is conformant if its behavior across a binding conforms. On-device execution changes nothing in Core. End-to-end encrypted storage is defined in 4.8, and G1.4 describes such deployments.

## G1.4 End-to-End Encrypted Deployments

Δ NEW (v2-draft-3) --- What a deployment that declares `e2e` should plan for (ST1--ST6).

Under `e2e`, the HCP Provider stores ciphertext, and a component the person controls does the work that needs to read it (4.8). That has consequences a deployment should plan for.

- **Reachability.** A query needs the trust-domain component. Where it runs on a phone that is off or out of coverage, the query fails with subject unavailable and the client tries later. Deployments where people are often offline, or share devices, should weigh this before choosing `e2e` (G3).
- **Keys.** If the person loses every copy of their keys, their content is lost with them. Recovery that does not hand the keys to the operator needs designing: a recovery key the person keeps, or keys held by several of their own devices.
- **What the operator still sees.** Categories, timing and provenance stay readable (4.8). For some people, which categories they hold is itself sensitive; `e2e` does not hide it.
- **Erasure.** Destroying keys is a dependable way to make content unrecoverable, backups included (5.4.2).
