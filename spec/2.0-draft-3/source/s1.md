## 1.2 Layers

**Core** defines what is true regardless of how HCP is carried: the actors, the data model, the operations and their results, lifecycle, authorization semantics, disclosure and minimization, audit semantics, and the error taxonomy. Every implementation claiming any HCP conformance conforms to Core (Part I).

**A Binding** carries Core operations and representations over a specific protocol. It defines framing, operation names, protocol metadata, how authorization evidence is carried, response representation, and the mapping of Core errors. A binding MUST preserve the semantics Core defines and MUST NOT redefine the meaning of a Core operation or field.

**A Profile** adds stricter rules for a domain, a security posture, an evidence type, or a deployment pattern. A profile MAY make optional Core behavior mandatory, MAY narrow the choices Core permits, and MAY define additional fields through the extension mechanism. A profile MUST NOT weaken or contradict a Core requirement, and MUST NOT redefine the meaning of a Core operation or field. Core MAY require a profile of any implementation that does a stated thing; the Memory Manager Profile (15) and the Health and Education Context Profiles (16) are required in this way.

**An Implementation Guide** assembles Core, bindings, and profiles for a use case and adds examples, recommended packages, deployment practice, and interaction patterns. Implementation Guides are non-normative. A guide that needs a rule MUST cite a profile that states it; a rule stated only in a guide is not a requirement of this specification.

There is one canonical meaning for every HCP operation and object, however many bindings carry it and however many profiles constrain it.

## 1.3 Sorting Requirements

Every requirement in this specification, and every requirement proposed for it, is placed by the following questions, asked in order. The first answer of yes places it.

1. Does the requirement define meaning that must be identical everywhere? → **Core**.
2. Does it name HTTP, MCP, framing, headers, methods, tool names, or protocol-specific errors? → **Binding**.
3. Is it a stricter rule for one domain, security posture, evidence type, or deployment pattern? → **Profile**.
4. Does it describe algorithms, storage, user experience, examples, deployment choices, or recommended practice? → **Implementation Guide**.

Applied to requirements carried over from HCP v1:

| Requirement | Placement |
|------------------------------------------------------------------|------------------------------------------------|
| Content that arrives before a grant authorizing its handling produces no entry, no audit event, and no state visible to a Context Client | Core (4) |
| A conflicted entry is not returned to a Context Client | Core (4) |
| Entries in `health_context` are treated as high-sensitivity | Health Context Profile (16) |
| Recording the party who authorized a grant on a minor's behalf | Delegated Authorization Profile (17) |
| The matching rule and normalization used to detect a conflict | Memory Manager Profile (15) |
| Temporary access is the default outcome of authorization | Core (6) |
| Authorization Code with PKCE | OAuth Interop Profile (13) |
| Return status 403 for an unauthorized request | HTTP Binding (9) |
| Return the Core error not authorized | Core (5) |
| Education credentials use Open Badges 3.0 | Education Context Profile (16.4) |
| Confirming a grant by voice in two prompts | Implementation Guide (G4) |

## 1.4 The Interface Boundary

HCP governs behavior at the interface boundary, not internal storage. Core states this as a requirement at the start of Part I. Every requirement in Core, the bindings, and the profiles is therefore written as behavior observable across a binding or in an export. Where a requirement names a field, it names the field as exchanged, not as stored.

## 1.5 Bindings and Transports

A binding carries HCP over another protocol. This specification defines two: the HTTP Binding (9) and the MCP Binding (10). "Transport" is used only in its MCP sense, for MCP's own stdio and Streamable HTTP transports, which sit beneath the MCP Binding.

Core defines one request schema and one result schema for each operation, and one error taxonomy (5). Each binding maps them:

- A binding MAY expose a subset of an operation's fields. It MUST NOT give any field a different meaning.
- A restriction on what a caller may do is a Core rule, not a property of a binding's shape. That a Context Client cannot create an `issuer-attested` entry or an entry whose content is a credential follows from Core (3.7), not from the fields an MCP tool happens to accept.
- The HTTP Binding maps Core errors to HTTP status codes and problem types. The MCP Binding maps them to tool execution errors. The mappings are in 9 and 10.

The discovery document declares the bindings an implementation exposes as `"bindings": ["http", "mcp"]` (19). This replaces v1's `supported_transports`.

## 1.6 Context Plane and Governance Plane

Δ CHANGED (v2-draft-3) --- Governance now changes an entry's categories and restricts its purposes (K1, K4). Directives are set on the governance plane (DA1). A client reports onward sharing on the context plane (OS7).

HCP operations fall on one of two planes.

| Plane | Operations | Who may call | Bindings |
|-------------------|------------------------------------------------------------|---------------------------------|---------------------|
| Context | Query, get an entry, create, revise, withdraw (soft delete only); an HCP Client reading or relinquishing its own grant, or reporting onward sharing (3.12) | Any HCP Client holding a grant that covers the operation (6) | HTTP and MCP |
| Governance | List grants; revoke a grant; read the audit log; read the disclosure summary; export and import; hard delete; confirm or reject an entry (3.8); change an entry's categories (4.5); restrict its purposes (4.2.6); set or remove a standing rule (6.3); set or remove a directive (6.4) | A Management Client acting for the Authorizing Principal (3.2.3) | HTTP only |

Core restricts governance operations to a Management Client acting for the Authorizing Principal (6), and the MCP Binding carries none of them (10). A Management Client can also perform context operations.

The planes divide operations, not events. Operations on both planes produce audit events (8); reading the audit log is a governance operation.

A binding is not a modality. The person-facing capabilities required by 18 can be offered through any modality the implementation supports, including natural language in an LLM-mediated interface. Where that interface is an HCP Client, it reaches governance operations as a Management Client over the HTTP Binding. A provider whose only binding is MCP, permitted under the First-Party package (18), offers those capabilities through its own person-facing interface rather than through an HCP binding.

## 1.7 Conformance Identifiers

Δ CHANGED (v2-draft-3) --- An identifier for the first client claim, following directives (DA6). Until v2 is final, a draft may break compatibility with the draft before it (RS11).

Core, each binding, and each profile has its own versioned conformance identifier. An implementation states what it conforms to as a `conformsTo` list of these identifiers in its discovery document (19). This replaces v1's single `conformance_level`. Because claims name Parts rather than the release package, they remain valid if the Parts are later published separately.

Identifiers in this draft use the placeholder domain hcp.example. The permanent namespace will be fixed before v2 is final; the maintainers hope to secure hcp.me for it. Conformance identifiers are compared as exact strings and need not resolve (19), so a later move of the specification's location does not invalidate a claim.

Packages name the combinations most implementations claim. They are defined in 18:

| Package | Comprises | v1 equivalent |
|---------------------|----------------------------------------------------------------------------------|---------------|
| First-Party | Core + General Context + any one binding + First-Party Authorization | Core |
| Provider Interop | Core + General Context + HTTP Binding + OAuth Interop | Interop |
| Agent Interop | Provider Interop + MCP Binding | None |
| VC Evidence | Adds to any package | VC-Extended |

An implementation that accepts HCP Clients operated by anyone other than its own Provider Operator is required to claim Provider Interop (18).

Until v2 is final, a draft may break compatibility with the draft before it. Each draft's changes to the wire are listed in its changelog entry (P3).

## 1.8 Requirements Language

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL are to be interpreted as described in BCP 14 (RFC 2119, RFC 8174) when, and only when, they appear in all capitals. Sections and passages marked informative contain no requirements.

## 1.9 Building Blocks

Δ NEW (v2-draft-3) --- HCP's building blocks, as the Introduction (I3) and the Terms name them (RS3).

HCP is built from six building blocks. They name what the Specification defines; they do not reorder it.

| Building block | What it defines | Where |
|----------------|------------------------------------------------------------------------|--------|
| Entries | The record of one piece of context: content, assertion, classification, evidence, and record, with provenance and lifecycle | 3, 4 |
| Grants | The Authorizing Principal's permission for one HCP Client: categories, actions, purposes, duration, and revocation | 6.1, 6.2, 12, 13, 17 |
| Disclosure | What a Context Client receives: minimized, with grant-scoped references and a use-until time | 5.2, 7 |
| Rules | Standing rules the provider enforces across every grant, and directives that clients follow | 6.3, 6.4 |
| Audit | The Context Subject's log of every grant, access and change, and its integrity | 8 |
| Discovery | The document in which an implementation describes what it supports | 19 |

## 1.10 Data Formats

Δ NEW (v2-draft-3) --- Times are RFC 3339 date-times (Q46).

Every time in this specification is a date-time as defined by RFC 3339 (section 5.6): a profile of ISO 8601 that always carries a time zone offset, such as `2026-11-05T20:23:00Z`. Templates write it as `{date-time}`. JSON Schema's `date-time` format, which the published schemas use (A.2), is the same profile.
