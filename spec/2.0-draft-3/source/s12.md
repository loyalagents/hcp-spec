# 12. First-Party Authorization Profile

## 12.1 Scope

This profile permits grants to be obtained through an authenticated channel other than OAuth 2.0, for HCP Clients operated by the Provider Operator. It is identified as https://hcp.example/spec/profiles/first-party-authorization/2.0 (1.7), and it is the authorization profile of the First-Party package (18). It replaces v1's `"authorization_profile": "first-party"`.

An implementation claiming this profile accepts only first-party clients: HCP Clients whose Client Operator is the Provider Operator. An implementation that accepts, or holds itself out as accepting, authorization requests from any HCP Client it does not itself operate MUST claim the OAuth Interop Profile instead (13, 18).

## 12.2 Requirements

An implementation claiming this profile:

- MUST satisfy 6.1.6 in full;
- MUST list this profile's identifier in `conformsTo`, and MUST NOT list the OAuth Interop Profile's (19);
- is not eligible for the Provider Interop or Agent Interop packages (18).

The authenticated channel may be an in-application session, a messaging interface, or an LLM-mediated dialogue (6.1.6). This specification does not mandate a wire-level request format for it; the channel supplies its own mechanism for a client to name the categories and actions it needs. What is mandated is the outcome specified in 6.1.6 and 6.1.7: before the Authorizing Principal acts, they MUST be told what 6.1.6 lists, and the act MUST be recorded as a `grant.issued` event. The grant is recorded as 6.1.5 specifies, with its `access` and the purposes approved; where the client names no purpose, the Authorizing Principal chooses one in the channel (6.1.5.2).

Where an implementation claiming this profile issues access or refresh tokens, their lifetimes MUST NOT exceed the maxima in 13.4.

The `conformsTo` declaration is authoritative. A client finding this profile's identifier in a discovery document can determine that it cannot obtain authorization from that implementation, whatever is claimed for the implementation elsewhere. This specification places requirements on what an implementation publishes, not on how it is described.

A conformance suite still needs a means to obtain a credential and trigger grant creation from an implementation claiming this profile. The test hook for this purpose is described in 20.

## 12.3 On the Deviation (Informative)

First-party-only conformance forgoes cross-implementation portability, which is the principal purpose of this specification. It is a defensible posture for a pilot validating other aspects of the protocol under real constraints. It is not a durable end state, and an implementation adopting it should expect to implement the OAuth Interop Profile before its context is expected to move to another provider.
