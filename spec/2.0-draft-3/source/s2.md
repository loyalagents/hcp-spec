# 2. Terms

Δ NEW (v2-draft-3) --- Terms by building block, then a mapping to OAuth (RS4).

This section is informative. It is a reader's map: each term is defined in the section it cites, and that section governs. The parties come first, then one table for each building block (1.9), then the terms HCP shares with OAuth.

## 2.1 Parties

Δ NEW (v2-draft-3) --- Who takes part (RS4).

| Term | Meaning |
|------------------------|------------------------------------------------------------------------|
| Context Subject | The natural person the context is about (3.2.1) |
| Authorizing Principal | Whoever governs a Context Subject's context and approves grants: the person, or a delegate (3.2.2, 17) |
| Delegate | A person who acts for a Context Subject under a delegation the HCP Provider records (17.1, 17.2) |
| HCP Client | Software that makes HCP requests and holds the grant it acts under; it is the security principal, not any model within it (3.2.3) |
| Management Client | An HCP Client acting for the Authorizing Principal; only it may perform governance operations (3.2.3) |
| Context Client | An HCP Client acting under a grant for a task; it performs context operations only (3.2.3) |
| HCP Provider | The service that holds context, enforces grants and rules, and keeps the audit log (3.2.4) |
| HCP instance | What a provider holds for one Context Subject: entries, grants and audit log (3.1) |
| Authorization Service | Authenticates the Authorizing Principal, presents what is asked, and issues grants (3.2.5) |
| Context Asserter | Whoever made the statement an entry records: the person, a model, or an issuer (3.2.6) |
| Requesting Party | Whoever the HCP Client is working for in a task (3.2.7) |
| Client Operator, Provider Operator | The organizations accountable for an HCP Client and for an HCP Provider (3.2.8) |
| Trust domain | Components the Context Subject controls, which read content when storage is end-to-end encrypted (4.8) |

## 2.2 Entries

Δ NEW (v2-draft-3) --- Terms for entries (RS4).

| Term | Meaning |
|------------------------|------------------------------------------------------------------------|
| Entry | One piece of context about a Context Subject: `content`, `assertion`, `classification`, `evidence` and `record` (4.2) |
| Declaration type | Whether the Context Subject stated the content, a model inferred it, or an issuer attested to it (4.4) |
| Basis | What an assertion was drawn from: a conversation, a document, an observation, an assessment, or other entries (4.2.5) |
| Confidence | A model's estimate for an inference, required only for `model-inferred` entries (4.4) |
| Category | A kind of context, registered or custom, that grants and rules name; an entry may be in several (4.5) |
| Sensitivity | Low, Medium or High, the default each category carries (4.5) |
| Permitted purposes | Purposes an entry may be disclosed for, set by its asserter or the Authorizing Principal (4.2.6) |
| Evidence | Items that make up or support an entry, such as a verifiable credential (4.2.2, 14) |
| Provenance | Who asserted, submitted and confirmed each version of an entry (3.5, 4.2) |
| Assurance | How strongly the HCP Provider established who the Context Asserter was (3.6) |
| Confirmation | The Context Subject's confirming or rejecting what was attributed to them or inferred about them (3.8) |
| Status | Where an entry stands in its lifecycle: `active`, `deprecated`, `conflicted`, `expired`, `revoked`, `suspended` or `deleted` (4.2.4) |
| Conflict | Two entries about the same thing that cannot both hold; standing decides which prevails (4.7) |
| Proposal | A client's suggested resolution of a conflict, which only the Authorizing Principal can act on (4.7.4) |
| Storage posture | `server`, or `e2e` where the provider cannot read entry content (4.8, A.1) |

## 2.3 Grants

Δ NEW (v2-draft-3) --- Terms for grants (RS4).

| Term | Meaning |
|------------------------|------------------------------------------------------------------------|
| Grant | The Authorizing Principal's permission for one HCP Client: what it may do, with which categories, for which purposes, until when (6.1, 6.1.5) |
| Authorization detail | One element of a grant's `access`: categories, actions, purposes, and any narrowing or onward sharing (6.1.5) |
| Action | `read`, `write` or `provenance` (6.1.5) |
| Purpose | A code naming what context may be used for; a grant names its purposes (6.1.5.2) |
| Temporary grant, persistent grant | A grant that ends with the interaction, and one the Authorizing Principal elected to keep (6.1.4) |
| Narrowed grant | A grant whose `narrowedTo` limits it further than its categories (6.1.5.1) |
| Onward sharing | The Authorizing Principal's election that a client may tell organizations it deals with what a task needs from Low-sensitivity context (3.12, 6.1.4) |
| Context operation, governance operation | Operations on context under a grant, and operations that govern the instance, reserved to a Management Client (1.6) |
| Revocation | Ending a grant, and with it everything issued under it (6.2) |
| Legal retention | A copy a client declared it must keep by law, which revocation does not reach (6.2.5) |
| Delegation | The record that a delegate may act for a Context Subject, on what basis, with what scope, and until when (17) |

## 2.4 Disclosure

Δ NEW (v2-draft-3) --- Terms for disclosure (RS4).

| Term | Meaning |
|------------------------|------------------------------------------------------------------------|
| Disclosure | What a Context Client receives for one entry: only what the grant covers, minimized (7.4) |
| `ref` | A reference to a disclosed entry, valid only under the grant it was disclosed under (7.4) |
| Use-until | The time after which a client stops using what was disclosed (7.6) |
| Minimization | Limiting a response to the categories, purposes, quantity and relevance a request needs (7) |
| Relevance method | How the provider orders entries for a query: `lexical`, `semantic`, `llm` or `none` (7.3, A.1) |
| Onward disclosure | Passing disclosed context on; allowed within the client's own operator, and to other organizations only as 3.12 permits (3.12) |
| Provenance on request | The `provenance` action, under which a client receives an entry's provenance (7.4.1) |

## 2.5 Rules

Δ NEW (v2-draft-3) --- Terms for rules (RS4).

| Term | Meaning |
|------------------------|------------------------------------------------------------------------|
| Standing rule | A rule the Authorizing Principal sets once and the HCP Provider enforces across every grant, such as denying a category to an operator (6.3) |
| Directive | An instruction about what an agent may do with context, such as signing or passing it on, which clients that claim to follow directives obey (6.4) |
| Directive effect | `deny`, `ask-first` or `permit` (6.4, A.1) |
| Client conformance claim | A claim an HCP Client makes, such as following directives, recorded with its grants (6.4, A.1) |

## 2.6 Audit

Δ NEW (v2-draft-3) --- Terms for audit (RS4).

| Term | Meaning |
|------------------------|------------------------------------------------------------------------|
| Audit log | The record of every grant, access and change in an HCP instance, readable by the Authorizing Principal (8) |
| Event type | The kind of event a log entry records, from the list in 8.1 (8.1, 8.2) |
| Disclosure summary | A readable account of who received what, under which grant, and how long they may use it (8.6) |
| Integrity level | How tamper-evident the log is, from `append-only` to `anchored` (8.7, A.1) |
| Controller-side logging | The Provider Operator's own records, kept apart from the Context Subject's log, for obligations that log cannot meet (8.5) |
| Security event | A signed notification, such as a revocation, pushed to clients (9.9) |

## 2.7 Discovery

Δ NEW (v2-draft-3) --- Terms for discovery and conformance (RS4).

| Term | Meaning |
|------------------------|------------------------------------------------------------------------|
| Discovery document | The document in which an implementation says what it supports and where (19) |
| Conformance identifier | The versioned URI of a Part, binding or profile (1.7) |
| Conformance claim | The list of identifiers an implementation conforms to, in `conformsTo` (18, 19) |
| Package | A combination of claims, such as First-Party, Provider Interop or Agent Interop (18) |
| Binding | How operations are carried: the HTTP Binding (9) or the MCP Binding (10) |
| Profile | A Part III specification that an implementation may claim (11--17) |

## 2.8 HCP Terms and OAuth

Δ NEW (v2-draft-3) --- Where HCP's terms meet OAuth's, and why HCP keeps its own names (RS4).

3.2.10 maps the roles to OAuth, MCP and the Verifiable Credentials Data Model. This table gives the reason behind each name.

| HCP term | OAuth term | Why the HCP name |
|------------------------|------------------------|------------------------------------------------------------------------|
| HCP Client | Client | HCP also has clients authorized without OAuth, under the First-Party Authorization Profile (12), and the name keeps the client apart from any model inside it (3.2.3) |
| HCP Provider | Resource server | It does more than serve protected resources: it records provenance, enforces standing rules, and keeps the person's audit log (3.2.4) |
| Authorization Service | Authorization server | It is a role, which may be part of the provider; under the OAuth Interop Profile it is the authorization server (3.2.5, 13) |
| Authorizing Principal | Resource owner | A delegate can authorize for another person, so the one who approves and the one the context is about are named separately (3.2.2, 17) |
| Context Subject | Resource owner, usually | The person the context is about stays the subject whoever authorizes (3.2.1) |
| Grant | Authorization grant, with the consent behind it | An OAuth grant is a credential for obtaining tokens; an HCP grant is the lasting record of what was approved, which governs every token issued under it (6.1.5) |
| Authorization detail | Authorization details (RFC 9396) | The same structure; HCP adds purposes, narrowing and onward sharing (6.1.5) |
| Category | Scope | Scopes are derived from categories (6.1.1); a category also carries a sensitivity and consent rules that a scope string does not (4.5) |
| Revocation | Token revocation | Revoking a grant ends every token issued under it, and clients are told (6.2) |
| Requesting Party | --- | OAuth does not model who a client acts for in a task; the term follows UMA's (3.2.7) |
