# 8. Audit

The audit log is append-only, inspectable by the Context Subject, and required for every implementation conforming to Core. Its level of tamper-evidence is declared (8.7).

## 8.1 Required Log Events

Δ CHANGED (v2-draft-3) --- `context.restricted` is new (K4). `conflict.proposed` is new, and `conflict.resolved` covers every conflict (M1, M2, M4). `directive.set` and `directive.removed` are new (DA9). `context.shared` is new (OS7).

| Event Type | Trigger |
|---------------------------|------------------------------------------------------------------|
| `context.created` | Any create (5.2.3) |
| `context.read` | Any query (5.2.1) or get entry (5.2.2) |
| `context.revised` | Any revise (5.2.4) |
| `context.recategorized` | Any change of an entry's categories (4.2.1) |
| `context.restricted` | Any change of the Authorizing Principal's permitted purposes for an entry (4.2.6) |
| `context.withdrawn` | Any withdraw (5.2.5) |
| `context.hardDeleted` | Any hard deletion (5.4.2) |
| `context.confirmed` | Any confirmation or rejection of an entry (3.8), with the disposition in detail |
| `context.exported` | Any export (5.4.1) |
| `context.imported` | Any import other than a dry run (5.4.3) |
| `context.shared` | A client reports sharing context with another organization (5.2.8) |
| `context.expired` | An entry's validity has passed, and its status is set to `expired` (4.2.4) |
| `context.credentialStatus` | An entry becomes or ceases to be `revoked` or `suspended`, or a supporting credential's `verification` changes with its status (14.7, 14.8) |
| `grant.issued` | Any new grant |
| `grant.revoked` | Any revocation |
| `grant.expired` | Automatic expiry of a grant, without revocation by the Authorizing Principal, including at the end of a delegation (17.6) |
| `delegation.established` | A delegation is established (17.2) |
| `delegation.ended` | A delegation ends (17.6) |
| `rule.set` | A standing rule is set (6.3) |
| `rule.removed` | A standing rule is removed (6.3) |
| `directive.set` | A directive is set (6.4) |
| `directive.removed` | A directive is removed (6.4) |
| `conflict.detected` | A conflict between two entries (4.7) |
| `conflict.proposed` | A proposal is made for resolving a conflict (4.7.4) |
| `conflict.resolved` | A conflict is resolved: a conflicted entry leaves conflicted status through any transition in 4.7.3, an asserter's later inference deprecates its earlier one, or a conflict that changed no status ends (4.7) |
| `revocation.notified` | Revocation notification sent to an HCP Client's notification endpoint (6.2.3) |

A `grant.expired` event MUST be appended no later than the earlier of (a) the first access attempt presenting the expired grant, or (b) 24 hours after the grant's expiry timestamp. Implementations are not required to append the event at the instant of expiry.

## 8.2 Log Entry Structure

Δ CHANGED (v2-draft-3) --- `categories` replaces `category`, and holds the categories of the entry the event concerns, or is absent; disclosures mark provenance; `context.restricted` data (K1, K4, K5). Conflict events: `conflict.proposed`, new transitions, and `proposal` on resolution (M1, M2, M4). Reads record the directives delivered; directive events (DA9). A sub-delegation's event names its parent (DL4). `grant.issued` records `acr` (SP6). `context.shared` data (OS7). Times are written as RFC 3339 date-times (1.10; Q46). Its example is labelled with what it is and who sends it to whom (RS5).

**Template: an audit event, as the HCP Provider records it**

    {
      "eventId": "urn:uuid:{uuid}",
      "eventType": "{event-type}",
      "timestamp": "{date-time}",
      "participants": {
        "initiator": { "role": "{role}", "id": "{identifier}" },
        "clientOperator": { "id": "{operator-identifier}" },
        "requestingParty": { "id": "{identifier}" },
        "authorizingPrincipal": { "id": "{identifier}" },
        "provider": { "id": "{provider-identifier}" },
        "retrievalId": "urn:uuid:{retrieval-uuid}",
        "model": { "id": "{model-identifier}" }
      },
      "entryId": "{urn:uuid or null}",
      "relatedEntryId": "{urn:uuid or null}",
      "categories": ["{category}"],
      "purpose": "{purpose code or null}",
      "purposeDescription": "{stated task or null}",
      "grantId": "{urn:uuid or null}",
      "disclosed": [
        {
          "entryId": "{urn:uuid}",
          "version": 2,
          "useUntil": "{date-time}",
          "provenance": true,
          "revealed": [ { "evidence": 0, "claims": ["{JSON Pointer}"] } ]
        }
      ],
      "data": { }
    }

`participants` replaces v1's `actorId` and `actorType`. `initiator.role` is one of `management-client`, `context-client`, `authorization-service`, or `hcp-provider`. Which members are present is set out in 3.9; no event names "system".

For `conflict.detected`, `conflict.proposed`, and `conflict.resolved`, `entryId` identifies the conflicted entry and `relatedEntryId` identifies the authoritative entry (4.7.1). Where neither or both are authoritative, they identify the two entries. `relatedEntryId` is null for all other event types.

`disclosed` is present on `context.read` and lists every entry disclosed by the retrieval: its stable `id`, the version disclosed, and the `useUntil` it was given (7.6). `provenance` is true where the disclosure carried provenance (7.4.1), and omitted otherwise. Where a credential was disclosed in derived form, `revealed` names the evidence item by its index and lists the claims revealed (14.9); it is omitted otherwise. The log names entries by their `id`, not by the `ref` the client received, because the log is the Context Subject's (8.3). The query text is not recorded: it can be as sensitive as the content it asks for.

`data` replaces v1's free-text `detail`. Its members are fixed by event type, so that the log can be filtered, tested, and presented in any language. Where this specification says that an event records something in detail, it is recorded in `data`.

| Event type | `data` members |
|---------------------------|------------------------------------------------------------------|
| `context.created`, `context.revised` | `version`; `reason` (revise) |
| `context.read` | `maxEntries` (query); `categoriesSearched` (query); `directives`, the `directiveId` of each directive the result carried (6.4) |
| `context.recategorized` | `from`, `to` (each a list of categories) |
| `context.restricted` | `from`, `to` (each a list of purpose codes, or null) |
| `context.withdrawn` | `reason` |
| `context.confirmed` | `disposition`, `version` |
| `context.exported` | `options` (5.4.1) |
| `context.imported` | `outcomes`: each entry's `id` and outcome (5.4.3) |
| `context.shared` | `recipient` (`domain`, `name`), `entries` (each `id`), `purpose`, `sharedAt`, `permitted` (5.2.8) |
| `context.expired` | `version` |
| `context.credentialStatus` | `evidence` (the item's index), `role`, `status` (`revoked`, `suspended`, or `valid`), and `entryStatus`, the entry's status after the change |
| `grant.issued` | `access`, `grantType`, `expiresAt`, `modality`, `acr` (6.1.4, 6.1.6); `delegation`, where a delegate authorized it (17.4) |
| `grant.revoked` | none |
| `grant.expired` | `reason`: `expiresAt` or `delegation-ended` (17.6) |
| `delegation.established` | `delegationId`, `relationship`, `basis.method`, `basis.parent` (a sub-delegation), `scope` (17.2, 17.10) |
| `delegation.ended` | `delegationId`, `reason` (17.6) |
| `rule.set`, `rule.removed` | `ruleId`, `operators`, `requires`, `categories`, `setBy` (6.3) |
| `directive.set`, `directive.removed` | `directiveId`, `action`, `effect`, `categories`, `operators`, `setBy` (6.4) |
| `conflict.detected`, `conflict.resolved` | `transition` (resolved: `rejected`, `accepted`, or `superseded`, 4.7.3; `dismissed`, 4.7.3; `asserter-superseded` or `ended`, 4.7); `proposal` (resolved: true where the act followed a proposal, 4.7.4) |
| `conflict.proposed` | `act`, `entry`, `weighed`, `proposedBy` (4.7.4) |
| `revocation.notified` | `outcome` (`delivered` or `abandoned`), `attempts`, `lastUseUntil` (6.2.4) |

Implementations MAY add members to `data`. They are preserved and not interpreted (A.3).

## 8.3 Access to the Audit Log

Reading the audit log is a governance operation (5.4). The Authorizing Principal MUST be able to, through a Management Client or the person-facing capabilities required by 18:

- View the full audit log
- Filter by HCP Client, category, event type, and date range
- Export the audit log in JSON-LD format

Context Clients MUST NOT have read access to the audit log. Under the Delegated Authorization Profile, the Context Subject reads the whole log, and a delegate or former delegate reads the part 17.7 sets out.

## 8.4 Durability

The append-only requirement in 8 constrains ordering and immutability. It does not by itself specify when an acknowledged append becomes durable against process or host failure. Implementations differ here, and this specification requires the difference to be declared rather than assumed.

- Every event type other than `context.read` MUST be durable before the operation it records is acknowledged to the caller.
- `context.read` MAY be acknowledged before durability, provided the implementation declares a bounded durability window in its discovery document (19).
- A declared window MUST NOT exceed 10,000 milliseconds.
- An implementation that declares a window MUST disclose it wherever it presents the audit log to the person, expressed as what the person may be missing rather than as storage behavior. This requirement is modality-neutral: it applies equally to graphical interfaces, to spoken and voice presentation, and to natural language access (18). Where the audit log is presented by voice, the disclosure is spoken; the obligation is to convey what may be missing, in whatever modality the log is offered, not to render a particular visual element.
- An implementation that declares no window is asserting synchronous durability for all event types, and conformance testing MAY hold it to that.

This provision governs durability only. It does not relax the ordering, immutability, or completeness requirements in 8.1 through 8.3.

## 8.5 Controller-Side Logging

Δ CHANGED (v2-draft-3) --- Un-linkability is discussed in the Security and Privacy Considerations (SP7).

The log specified in 8.1 through 8.4 is the Context Subject's log. It is theirs to inspect and export, and Context Clients cannot read it (8.3).

Provider Operators are separately subject to obligations that a per-person log cannot discharge: organization-level access questions spanning many Context Subjects, and records that must survive hard deletion of a person's data in order to evidence that the deletion took place. Accordingly:

- Provider Operators are expected to maintain a controller-side access log. It sits outside the HCP instance and is not part of the HCP data model.
- The controller-side log MUST NOT contain entry content, in whole, in part, or in derived form.
- It MAY contain a pseudonymous subject identifier, participant identifiers, an event type, a category slug, a grant identifier, and a timestamp.
- It MAY retain these after the corresponding Context Subject's data has been hard-deleted, and MAY anchor the integrity of the Context Subject's log.
- The prohibition in 8.3 applies to the Context Subject's log. It does not prohibit the controller-side log.
- The controller-side log SHOULD be designed so that it cannot be cross-matched against the Context Subject's own log to reconstruct entry content or infer it from access patterns. A pseudonymous subject identifier that is stable across the Provider Operator's whole population, for instance, lets the two logs be joined; a per-person or rotating pseudonym resists that. Preserving this un-linkability is discussed in 21.6; for now it is a design expectation, stated so that implementations do not build a scheme that has to be undone.
- Conformance testing does not evaluate the controller-side log.

## 8.6 Disclosure Summary

Δ CHANGED (v2-draft-3) --- The shape of each member is stated (J9). Times are written as RFC 3339 date-times (1.10; Q46).

The HCP Provider MUST make available to the Authorizing Principal a summary of what each HCP Client has received. It is a governance operation (5.4), carried by the HTTP Binding (9.4.12), and a person-facing capability (18.4). For each client it gives:

| Member | Content |
|------------------------|------------------------------------------------------------------|
| `client` | Object: the client's `id` and `name`, and its `operator`, with `id` and `name` (3.2.8) |
| `grants` | Array: the grants under which it received context, each with `grantId` and `status` |
| `categories` | Array: the categories disclosed to it |
| `purposes` | Array: the purpose codes declared for those disclosures (6.1.5.2) |
| `entries` | Integer: how many distinct entries were disclosed |
| `retrievals` | Integer: how many retrievals there were |
| `firstAt`, `lastAt` | Date-time: the period over which they took place |
| `usableUntil` | Date-time: the latest `useUntil` among the copies disclosed (7.6), or, where a revocation notice was delivered, the time of delivery |
| `notification` | `delivered`, `abandoned`, or `none`, for the most recent revocation (6.2.4) |
| `legalRetention` | Object: `record`, `obligation` and `period`, as in the grant, where the client declared one (6.1.5, 6.2.5) |

The summary is computed from the audit log (8.2) and MAY be filtered by client, category, and date range. It discloses nothing the log does not hold. It does not show what happens to context after it reaches a client, which the provider cannot see (6.2.2).

## 8.7 Integrity

Δ CHANGED (v2-draft-3) --- At least `hash-chained` for providers holding High-sensitivity categories (SP7).

Append-only means the log cannot be altered through any HCP operation. It does not, by itself, let anyone detect an alteration made outside them. An HCP Provider MUST declare the integrity of the Context Subject's log in its discovery document as `audit_integrity` (19). One that holds entries in a High-sensitivity category (4.5) SHOULD declare at least `hash-chained` (21.6):

| Value | Meaning |
|------------------------|------------------------------------------------------------------|
| `append-only` | Events cannot be changed or removed through any HCP operation. The minimum for conformance. |
| `hash-chained` | Each event carries a hash of the one before it, so a change to any event is detectable |
| `signed-checkpoints` | As `hash-chained`, with the chain's head signed by the provider at intervals |
| `anchored` | As `signed-checkpoints`, with checkpoints recorded outside the provider's control, for example in the controller-side log of another party (8.5) |

How hashes are computed and checkpoints published is not specified in this draft. The declaration makes the level explicit and testable; pilots that need more than `append-only` will inform a common format (P1).
