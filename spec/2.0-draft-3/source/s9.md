# Part II --- Bindings

# 9. HTTP Binding

## 9.1 Scope

This section maps the Core operations (5) and errors (5.5) onto HTTP. It is identified as https://hcp.example/spec/bindings/http/2.0 (1.7).

The HTTP Binding exists for traditional, auditable server-to-server integration --- institutional systems, batch jobs, and clients that are not LLM-mediated --- where a conventional HTTP client is the natural fit; the MCP Binding (10) exists for agent-native access, where an LLM discovers and invokes tools directly. The HTTP Binding is also the only binding that carries governance operations (1.6), and it is required for the Provider Interop package (18).

The base URL is implementation-defined. An implementation exposing the HTTP Binding MUST publish a discovery document at `/.well-known/hcp-configuration` (19).

## 9.3 General Requirements

All requests MUST include a Bearer token in the Authorization header. Successful responses are `application/ld+json`. Error responses are `application/problem+json` (9.7).

**Protocol version.** Every response, including error responses and responses with no body, MUST carry an `HCP-Version` header whose value matches the `hcp_version` published in the implementation's discovery document. Responses do not carry an `hcp_version` member in the body.

Clients MAY send an `HCP-Version` request header naming the protocol version they expect. An implementation that does not support the requested version MUST respond with unsupported version (9.7), and MUST NOT silently serve a different version.

## 9.4 Operations

### 9.4.1 Query

Δ CHANGED (v2-draft-3) --- The result carries `directives` (DA9). Times are written as RFC 3339 date-times (1.10; Q46). Examples are concrete HTTP messages, labelled by direction (RS5, RS9).

`POST /v2/entries/query`. The request body carries the fields in 5.2.1:

**Request: Context Client → HCP Provider (HTTP)**

    POST /v2/entries/query HTTP/1.1
    Host: provider.example
    Authorization: Bearer eyJhbGciOiJFUzI1NiJ9.eyJzdWIiOiJ…
    Content-Type: application/json

    {
      "query": "footwear constraints for hiking",
      "categories": ["health_context"],
      "purpose": "https://purposes.example/product-recommendation",
      "purposeDescription": "Choosing hiking boots",
      "maxEntries": 5
    }

`maxEntries` defaults to 5 and is subject to the ceiling in 7.2.

Response (200):

**Response: HCP Provider → Context Client (HTTP)**

    HTTP/1.1 200 OK
    Content-Type: application/json

    {
      "entries": [ ],
      "retrievalId": "urn:uuid:3f2c8a1e-6b0d-4e7a-9c55-1d2e3f4a5b6c",
      "minimization": { "method": "lexical" },
      "categoriesSearched": ["health_context"],
      "directives": [ ],
      "timestamp": "2026-10-27T13:02:12Z"
    }

Each item in `entries` is a disclosure where the caller is a Context Client (7.4); 9.4.2 shows one.

### 9.4.2 Get Entry

Δ CHANGED (v2-draft-3) --- Example updated to `classification.categories` (K1). Times are written as RFC 3339 date-times (1.10; Q46). Examples are concrete HTTP messages, labelled by direction (RS5, RS9).

Response (200), shown for a General Context entry disclosed to a Context Client (7.4):

### 9.4.3 Create

`POST /v2/entries`. The request body carries the entry fields specified in 5.2.3, omitting those the HCP Provider assigns, plus the required top-level `purpose`. This purpose is request metadata, not part of the stored entry. Response (201): the created entry with provider-assigned fields populated, as a disclosure for a Context Client. The completion-only alternative (5.6) uses status 200.

**Request: Context Client → HCP Provider (HTTP; new assertion with no permitted content use)**

    POST /v2/entries HTTP/1.1
    Host: provider.example
    Authorization: Bearer eyJhbGciOiJFUzI1NiJ9.eyJzdWIiOiJ…
    Content-Type: application/json

    {
      "purpose": "https://purposes.example/trip-planning",
      "schema": "https://hcp.example/spec/entry/2.0",
      "subject": { "id": "urn:uuid:9a4b6c8d-2e1f-4a61-8b57-97ad11cc843f" },
      "content": {
        "profile": "https://hcp.example/spec/profiles/general-context/2.0",
        "value": "I prefer an aisle seat."
      },
      "classification": { "categories": ["general_preferences"] },
      "assertion": { "declarationType": "person-declared", "permittedPurposes": [] },
      "record": { "provenance": { "source": "synthetic-review" } }
    }

**Response: HCP Provider → original caller (committed create, representation withheld)**

    HTTP/1.1 200 OK
    Content-Type: application/ld+json
    HCP-Version: 2.0

    { "outcome": "committed", "representation": "not-included" }

The exact completion-only body uses 200 for create, revision, withdrawal and non-dry-run import (9.4.3–9.4.5, 9.4.11), including an authorized copy-expiry retry under 9.6. Ordinary create/revise responses retain 201. It carries no resource-specific `Location` or `ETag`. It is not a new 204 mapping or an HTTP preference that can override Core.

### 9.4.4 Revise

Δ CHANGED (v2-draft-3) --- Examples are concrete HTTP messages, labelled by direction (RS5, RS9).

`POST /v2/entries/{entryId}/revisions`. A revision is a new version, created as a subordinate resource of the entry. Request body:

**Request: Context Client → HCP Provider (HTTP)**

    POST /v2/entries/r_8Jq2vNw4TzL0/revisions HTTP/1.1
    Host: provider.example
    Authorization: Bearer eyJhbGciOiJFUzI1NiJ9.eyJzdWIiOiJ…
    Content-Type: application/json

    {
      "expectedVersion": 2,
      "purpose": "https://purposes.example/product-recommendation",
      "content": {
        "profile": "https://hcp.example/spec/profiles/general-context/2.0",
        "value": "I require high arch support and wide toe box in footwear.",
        "language": "en"
      },
      "reason": "Correction by the Context Subject during conversation"
    }

The body MAY also carry the optional fields in 5.2.4. Response (201): the revised entry, with `record.version` incremented by 1, as a disclosure for a Context Client. The completion-only alternative (5.6, 9.6) uses status 200. The entry's `id` is unchanged by a revision. Where `expectedVersion` is not the current version, the response is version conflict (9.7), except that an authorized idempotent retry follows 9.6 without executing the revision again.

### 9.4.5 Withdraw and Hard Delete

Δ CHANGED (v2-draft-3) --- Times are written as RFC 3339 date-times (1.10; Q46). Examples are concrete HTTP messages, labelled by direction (RS5, RS9). A Context Client names the entry by its `ref` and receives the `ref` back, never the `id` (Q48).

`DELETE /v2/entries/{entryId}` withdraws an entry (5.2.5). With the query parameter `hardDelete=true` it hard-deletes the entry instead (5.4.2), which only a Management Client may do (6.1.9).

For soft withdrawal, the request MUST carry a JSON body with `purpose` and `reason` (5.2.5), using `Content-Type: application/json`. HCP HTTP providers MUST accept this body; clients and deployments must ensure it reaches the provider through any intermediaries. This is the HCP mapping, not a property of generic HTTP DELETE support. The hard-delete governance request gains neither field from this mapping.

Withdrawal can instead return the completion-only result (5.6), with status 200. Hard deletion retains its own result and erasure requirements; it does not gain that alternative from sharing this endpoint or a result schema.

The result names the entry as the caller named it (5.2.5): a Context Client names it by its `ref` and receives the `ref` back, never the `id`. A Management Client withdraws an entry by its `id`:

**Request: Management Client → HCP Provider (HTTP)**

    DELETE /v2/entries/urn:uuid:7d1e4b2a-0c9f-4a61-8e3d-5b6a7c8d9e0f HTTP/1.1
    Host: provider.example
    Authorization: Bearer eyJhbGciOiJFUzI1NiJ9.eyJzdWIiOiJ…
    Content-Type: application/json

    {
      "purpose": "https://purposes.example/trip-planning",
      "reason": "Remove this preference."
    }

Response (200):

**Response: HCP Provider → Management Client (HTTP)**

    HTTP/1.1 200 OK
    Content-Type: application/json

    {
      "entryId": "urn:uuid:7d1e4b2a-0c9f-4a61-8e3d-5b6a7c8d9e0f",
      "status": "deleted",
      "hardDeleted": false,
      "timestamp": "2026-10-27T15:40:00Z"
    }

### 9.4.6 Grants

Δ CHANGED (v2-draft-3) --- Revoking or relinquishing a grant responds 204 (J8).

`GET /v2/grants` returns grant objects (6.1.5). Access is scoped by caller:

- Called by a Management Client acting for the Authorizing Principal, it returns all grants. An optional `status` query parameter filters by status; the default is `active`.
- Called with a Context Client's bearer token, it returns only the grant under which that token was issued.

Responses MAY be paginated per 9.5.

`DELETE /v2/grants/{grantId}` revokes a grant (6.2). Called by a Management Client, it revokes any grant for the instance. Called with a Context Client's bearer token, it relinquishes the grant under which that token was issued (5.2.7); naming any other grant fails with not authorized. Response (204), with no body, in either case.

### 9.4.12 Disclosure Summary

`GET /v2/disclosures`, with the optional query parameters `client`, `category`, `from`, and `to`. Response (200): a `clients` array, one member per HCP Client, each carrying the members in 8.6. It MAY be paginated per 9.5.

### 9.4.13 Delegations

An implementation conforming to the Delegated Authorization Profile (17) exposes:

- `GET /v2/delegations`. Response (200): a `delegations` array of delegation objects (17.2), with ended ones where `status=ended` is asked. A Management Client acting for the Context Subject receives every delegation for them; one acting for a delegate receives only the delegations naming that delegate.
- `DELETE /v2/delegations/{delegationId}`, by a Management Client acting for the delegate it names: relinquishes the delegation (17.6). Where the delegation's basis is `appointed`, a Management Client acting for the Context Subject may also call it, which ends the delegation with reason `ended-by-subject`. Response (204). Any other caller receives not authorized.

A delegation is established by the Authorization Service, not through this binding (17.2).

### 9.4.14 Standing Rules

Δ CHANGED (v2-draft-3) --- A rule may name `requires` (DA7).

- `GET /v2/rules`. Response (200): a `rules` array of standing rules (6.3).
- `POST /v2/rules`, with `operators`, `requires`, or both, and optionally `categories`. Response (201): the rule, with its `ruleId` and `createdAt`. The HCP Provider sets `effect` to `deny`.
- `DELETE /v2/rules/{ruleId}`. Response (204).

Each is called by a Management Client acting for the Context Subject, or, under the Delegated Authorization Profile, for a delegate within the delegation's scope (6.3). A delegate's `DELETE` succeeds only for a rule they set. Any other caller receives not authorized.

### 9.4.15 Directives

## 9.5 Pagination

`GET /v2/audit` MUST support cursor-based pagination:

| Parameter | Location | Description |
|-----------|-----------------|------------------------------------------------|
| `cursor` | Query, optional | Opaque continuation token from a prior response |
| `limit` | Query, optional | Maximum events in this page |

Responses carry a `nextCursor` member holding an opaque token, or null when the result set is exhausted. Cursors MUST be opaque to clients, MUST NOT encode credentials or entry content, and MUST remain valid for at least 300 seconds.

A bare sequence number or offset does not satisfy the opacity requirement. A pilot implementer asked whether a plain incrementing integer may serve as a cursor (Turn.io); it may not, because a monotonic cursor discloses the total number of audit events to any client that receives one, which is itself information about the volume of a person's activity. An opaque cursor may be an encrypted or signed offset, or a server-side handle; what it MUST NOT be is a value from which a client can read the size or position of the underlying set.

`POST /v2/entries/query` is not paginated (7.2).

## 9.6 Idempotency

`POST /v2/entries` and `POST /v2/entries/{entryId}/revisions` MUST accept an `Idempotency-Key` request header, and clients SHOULD send one. `DELETE /v2/entries/{entryId}` SHOULD accept it; clients MUST NOT automatically retry withdrawal unless support is known. This section adds no key to import or MCP tool arguments, and does not authorize automatic retries of unkeyed operations.

**Identity.** The key namespace is the provider's instance for the Context Subject, the authenticated HCP Client, and its context or management capacity. Bind a committed key to its original grant or management authorization, operation, exact target and identical UTF-8 body octets. Whitespace and member ordering differences count as differences; raw bodies need not be retained to compare them. Another grant MUST NOT make the same consumed key fresh or expose its match, conflict or result. Refreshing a token under unchanged authority preserves the namespace; re-registration that changes the authenticated client identity does not recover the old operation.

**Effects and durability.** A protected keyed write MUST cause at most one mutation and one set of required operation events, including through concurrent requests, lost replies and restart. Duplicate protection MUST last at least 24 hours from successful commit. Recovery MUST preserve the operation, its required durable audit and its key/result binding so a committed write cannot execute again. This specifies observable recovery, not a database layout or transaction spanning every store. Providers MAY retain protection longer. Confirmed no-effect failures do not consume a fresh key; denial of a retry does not clear a key consumed earlier. While an operation may have committed, it MUST NOT be executed again.

**Original result.** At commit, establish a role-correct result candidate: the ordinary representation where authorized, otherwise the fixed completion-only result (5.6). The provider MAY store a response or enough information to reproduce it. The original result means its associated success status and JSON member values, including time-varying values as selected at commit, not serialization bytes or transport headers. It MUST NOT be replaced with current entry data, reprojected content, refreshed standing or a renewed copy deadline. Resource-specific headers still require current release authority.

The candidate is distinct from the reply actually sent. For example, token expiry after commit can make the original reply completion-only; refreshed evidence for the same unchanged grant can recover a still-eligible ordinary candidate. A write-only completion candidate cannot become a content or reference result after widening. An ordinary Context Client create/revise candidate carries `ref` and `version`, never the stored `id` and `record.version` (7.4). An ordinary withdrawal acknowledgement retains the original request's `ref` or `entryId`; completion carries neither.

**Current authority.** Every retry requires fresh authentication and current authority for both the presented operation and the historical operation/result under the same original authorization. These checks MUST precede any key-dependent reply, including completion, conflict or temporary uncertainty. Do not rerun optimistic-version or other execution preconditions consumed by the original successful operation. Invalid evidence yields unauthenticated. Insufficient authority, a replacement grant or an ineligible historical result yields opaque not authorized, except for the exact copy-expiry case below; do not disclose prior existence or outcome. Only an otherwise-authorized mismatch against an eligible historical result yields `idempotency-conflict`.

Current active lifecycle, current and selected-version purpose/validity restrictions, and the original `useUntil` govern content-bearing Context Client results. Their disclosure is evaluated for the original request's named purpose (5.6), never a substitute purpose. A historical withdrawal acknowledgement may remain authorized after withdrawal because it discloses no entry content. A retained completion candidate requires current authority for its original operation, target and named purpose under the original grant (6.1.5.2), but no read reach or membership in the entry's permitted-purpose lists. The presented operation also requires its named purpose to be authorized; changing that field changes the request and does not recover or refresh a historical result. Management results retain their management scope and do not acquire a Context Client copy deadline.

**Exact retry result.** Within the protected interval, an exact authorized retry MUST return the eligible original candidate and its original success status without a second mutation or operation event. There is one copy-expiry exception: if the operation and required audit are known committed and the original content copy's `useUntil` is the sole failed eligibility condition, the exact retry MUST instead return the fixed completion object (5.6) with HTTP 200 and no resource-specific headers. All other authority, lifecycle, selected-version and validity conditions still apply. An assertion or credential that has itself expired is not copy-only expiry. No content, identifier, fresh copy or extended deadline accompanies this result.

A mismatch in operation, target or body cannot use the expiry exception. If its historical result is ineligible, including through copy expiry, it receives opaque denial before any conflict detail. Other ineligibility or permission invalidation also denies an exact retry; it cannot be converted to completion. The exception discloses only the historical commit and does not continue the original request's entitlement.

**Permission changes.** An effective permission change MUST permanently invalidate each prepared or retained candidate whose authorization it actually affects, including across narrowing then restoration. For retained HTTP candidates, a provider MAY conservatively invalidate all earlier candidates under a grant when that grant's permissions, or a governing policy applicable to it, genuinely change. Precise invalidation is also permitted; actually affected results MUST be invalidated in either case. Cached response payloads of every invalidated candidate MUST be discarded. Unrelated grants, clients and independent management authority retain their eligible results. Shared policy may affect several grants, but each must be within its scope. Token refresh without changed authority and semantically unchanged policy saves are not invalidation triggers.

Invalidation MUST survive restart and take effect no later than acknowledgement of the permission change. Invalidated candidates MUST NOT revive or qualify for the copy-expiry exception. Ordinary original-result release and revealing retry replies MUST be ordered against effective authority changes at the release decision; no stale prepared reply may escape after its invalidation. At that decision, a revealing retry reply MUST also satisfy all applicable eligibility conditions, including deadlines, subject only to the exact copy-expiry exception above. This requires neither a specific serialization callback nor waiting for delivery or remote receipt. Original-channel completion retains its limited entitlement under 5.6.

**Retained information.** Providers MAY discard replay-only Context Client content at its original `useUntil`, but MUST preserve duplicate protection and enough permitted historical context to establish the remaining retry conditions throughout the protected interval, including after restart. Eligible results MUST remain recoverable except for the invalidation permitted above; arbitrary early eviction is not an authorization change. This does not erase authoritative entry/history records or recipients' copies. Hard deletion (5.4.2) remains a separate obligation: these rules permit no retention of erased content and no resurrection through a protected old key. They do not settle what operation metadata may survive erasure or establish combined erasure/retry safety.

**Temporary uncertainty.** After the applicable authority checks, if execution is outstanding or its outcome is temporarily indeterminate during recovery, the provider MAY wait for a bounded period. If still unresolved when replying, it MUST return the HTTP-only `idempotency-unresolved` problem with status 503 and `Retry-After`. It MUST NOT execute the operation again while uncertain. Known ineligibility requires denial, not this temporary response. An unrecoverable committed-key state is a failed recovery guarantee, not permission to start fresh.

**Response: HCP Provider → HCP Client (authorized keyed operation temporarily unresolved)**

    HTTP/1.1 503 Service Unavailable
    Content-Type: application/problem+json
    HCP-Version: 2.0
    Retry-After: 1

    {
      "type": "https://hcp.example/problems/idempotency-unresolved",
      "title": "Idempotency outcome unresolved",
      "status": 503,
      "detail": "Retry the same request and key after the indicated delay."
    }

This is not a Core/MCP error or a new meaning for `subject-unavailable`; 409 `idempotency-conflict` remains a proven mismatch.

**Client recovery.** Preserve the method, target, key and exact bytes before first dispatch. With known idempotency support, clients MAY make bounded same-request/key retries under the original authority, respecting `Retry-After` or otherwise backing off. Stop comfortably within the supported interval, measured conservatively from first dispatch with delivery time allowed. A new key, replacement grant, changed client identity or expired protection window is not automatic recovery. Corrected input may reuse an unconsumed key only when no attempt under it committed or remains unresolved.

Completion confirms success and the caller can stop; it does not explain why content was omitted or establish that no eligible reference can be recovered. A supported, authorized same-key attempt to recover that result may therefore still be useful. A denial says nothing about an unknown earlier outcome and does not undo known success. A proxy 5xx, timeout or dropped reply supplies no new confirmed outcome; it does not prove provider-side pending execution or rollback. Neither an error status nor a problem body alone establishes no effect. Never automatically resend an unsupported or unkeyed write merely because its reply was lost.

| Retry case within the protected interval | Required outcome |
|-----------------------------------------|------------------|
| Exact request, unchanged authority, eligible candidate | Original status and JSON values; one mutation and one set of operation events |
| Fresh token for the same unchanged grant; ordinary candidate still eligible after an original minimal or lost reply | Original eligible candidate and original deadline |
| Exact request; only the original content copy expired | Fixed HTTP 200 completion; no content, ref or resource headers |
| Changed body/operation/target; historical candidate still eligible and both contexts authorized | 409 mismatch; no effect |
| Changed body/operation/target; historical content copy expired | Opaque denial, not 409 or completion |
| Invalid evidence, replacement grant, invalidated result or other ineligibility | Authentication/authorization denial; no result-existence detail or new effect |
| Narrowing then restoration, or restart after precise or permitted conservative invalidation | Candidate stays invalid; committed key remains consumed |

A revision needs a key as much as a create: without one, a repeat may fail its consumed expected-version check without identifying the original success. An unsupported or unkeyed repeated withdrawal can append another event even though the entry stays deleted. These cases do not justify new keys for uncertain operations.


## 9.7 Errors

Δ CHANGED (v2-draft-3) --- Subject unavailable maps to 503 (ST3).

All error responses MUST use `application/problem+json` per RFC 9457, carrying at minimum `type`, `title`, `status`, and `detail`. Implementations MAY add extension members.

Each Core error (5.5) maps to one status. The binding-only `idempotency-unresolved` condition has no Core or MCP code. Problem types below are relative to https://hcp.example/problems/:

| Core error (5.5) or HTTP-only condition | Status | Problem type |
|-----------------------|--------|------------------------|
| invalid request | 422 | `malformed-request` |
| unauthenticated | 401 | `invalid-token` |
| not authorized | 403 | `scope-denied` |
| conflict | 409 | `idempotency-conflict` |
| version conflict | 409 | `version-conflict` |
| credential invalid | 422 | `credential-invalid` |
| subject unavailable | 503 | `subject-unavailable` |
| temporarily unresolved keyed operation (HTTP only, 9.6) | 503 | `idempotency-unresolved` |
| rate limited | 429 | `rate-limited` |
| unsupported version | 400 | `unsupported-version` |

A `scope-denied` response MUST NOT disclose whether the requested entry exists (5.2.2).

## 9.8 Rate Limiting

A 429 response MUST include a `Retry-After` header. Implementations SHOULD publish their rate limit policy in the discovery document (19).

Rate limiting MUST NOT be applied to `DELETE /v2/grants/{grantId}` (6.2.1).

## 9.9 Revocation Notification Delivery

Δ CHANGED (v2-draft-3) --- Times are written as RFC 3339 date-times (1.10; Q46). Examples are concrete HTTP messages, labelled by direction (RS5, RS9).

Where an HCP Client has registered a notification endpoint, the notification required by 6.2.2 is a Security Event Token (SET, RFC 8417), delivered to that endpoint by push delivery (RFC 8935).

**The token.** The provider delivers the SET to the client's notification endpoint:

**Notification: HCP Provider → HCP Client (HTTP push, RFC 8935)**

    POST /hcp/events HTTP/1.1
    Host: client.example
    Content-Type: application/secevent+jwt

    eyJhbGciOiJFUzI1NiIsImtpZCI6InByb3ZpZGVyLTIwMjYifQ.eyJpc3MiOi…

Its payload, decoded:

**Notification payload, decoded: HCP Provider → HCP Client**

    {
      "iss": "https://provider.example",
      "aud": "https://client.example",
      "jti": "urn:uuid:c4d5e6f7-a8b9-4c0d-9e1f-2a3b4c5d6e7f",
      "iat": 1793106300,
      "events": {
        "https://hcp.example/spec/events/grant-revoked": {
          "grantId": "urn:uuid:1a2b3c4d-5e6f-4a7b-8c9d-0e1f2a3b4c5d",
          "revokedAt": "2026-10-27T13:05:00Z"
        }
      }
    }

- `iss` is the HCP Provider, `aud` the HCP Client being notified, and `iat` the time the token was issued.
- `jti` identifies the notification. It is identical on every delivery attempt, and receiving clients use it to deduplicate.
- The event type is `https://hcp.example/spec/events/grant-revoked`. It names the grant revoked and when.

**Signing.** The SET MUST be signed with JWS using an asymmetric algorithm, with a key published in the JSON Web Key Set at the discovery document's `jwks_uri` (19). Receiving clients MUST verify the signature, and SHOULD reject a token whose `iat` differs from local time by more than 300 seconds.

**Delivery.** Delivery is an HTTP POST of the SET, with media type `application/secevent+jwt`, as RFC 8935 specifies. The client acknowledges receipt with 202 Accepted, or rejects the token with 400 and an RFC 8935 error code.

**Retry.** Delivery MUST be retried on connection failure and on any response other than 202 or 400, with exponential backoff, for at least 5 attempts over at least 1 hour before delivery is abandoned. Every attempt MUST carry the same token. A 400 response ends delivery and is recorded as abandoned, with the client's error code.

Auditing, abuse controls, and independence from revocation are Core requirements (6.2.3, 6.2.4).
